# Проект: Idle RPG — браузерная idle RPG

Idle/incremental RPG в духе классических MMORPG. Все названия, зоны, классы, предметы,
лор — **оригинальные**. Категорически запрещено использовать IP Blizzard: названия зон,
мобов, предметов, рас, классов, боссов и локаций из World of Warcraft, а также любые
их ассеты. При сомнении — придумывай своё.

## Стек

- Vite + Svelte + TypeScript
- Боевая сцена — двумерная, обычными элементами страницы (`src/lib/render2d/`).
  Движка нет: ни three, ни WebGL, ни канвы — сцена заводится в любом браузере
- break_infinity.js (класс `Decimal`) — для неограниченно растущих игровых величин
- Сохранение: localStorage, JSON, обязательное поле `version`
- Деплой: GitHub Actions → GitHub Pages, `base: '/idle-rpg/'`

## Команды

- Установка: `npm ci`
- Сборка: `npm run build`
- **Быстрый набор: `npm run test`** — типы, юниты, golden, проверка контента.
  Ни одного обращения к браузеру, ни одной матрицы прогонов. Около минуты.
  Сами юниты без проверки типов — `npm run test:unit` (его же зовёт CI). ВСЁ, ЧТО СТРОИТ ЭТАЛОННОЕ ПРОХОЖДЕНИЕ ИЛИ ГОНЯЕТ СИМУЛЯЦИЮ ПО
  ЛЕСТНИЦЕ, живёт в дорогом наборе, а не здесь: такие тесты стоят минутами,
  и один из них съедает быстрый набор целиком.
- Прогон баланса целиком: `npm run test:balance` (полная матрица плюс
  прогон полного пути и таблица обгона зон, ~11 минут на четырёх ядрах)
- Прогон баланса выборкой: `npm run test:balance:sample` (~3.5 минуты;
  чего она НЕ ловит — в разделе «Какие проверки когда»)
- Визуальная регрессия: `npm run test:visual` (сборка + скриншоты, ~6 минут)
- Всё вместе: `npm run test:all`
- Балансный отпечаток: `npm run balance:diff` (сверяет свежий дамп матрицы
  с `docs/balance-baseline.json` побитово; эталон переписывается
  `npm run balance:baseline` и только осознанно)
- Проверка контента отдельно: `npm run content:check`
- Проверка типов отдельно: `npm run check`
- Обновить эталоны скриншотов: `npm run screenshots:update` (ВСЕ разом)
- Обновить ОДИН эталон: `npm run screenshots:update:one -- "имя снимка"`.
  Именно им и надо пользоваться: полное обновление, запущенное ради одного
  уехавшего снимка, заодно узаконивает все остальные — включая настоящую
  регрессию, которую тогда уже никто не найдёт. Список имён —
  `npm run screenshots:list`.
- Перегенерировать пресеты состояний: `npm run presets:update`

## Какие проверки когда

ТРИ ЯРУСА, И РАЗЛИЧАЮТСЯ ОНИ СТОИМОСТЬЮ. Правило простое: во время работы
гоняется только первый, второй — после правки чисел, третий — перед merge.

| ярус | команда | сколько идёт | когда |
| --- | --- | ---: | --- |
| быстрый набор | `npm run test` | ~1 мин | на каждой правке, сколько угодно раз |
| проба баланса | `npm run test:balance:sample` | ~3.5 мин | после правки чисел баланса |
| полная матрица | `npm run test:balance` | ~11 мин | один раз перед PR и ночью на `main` |

Замеры сняты на четырёх ядрах. Полная матрица шла 49 минут, проба — 7.6;
матрицу разогнали разрезанием файлов и кешем оценки боя: раннер раскладывает по ядрам
ФАЙЛЫ, а не тесты, и 87 % работы лежало в одном файле (см. `docs/PERF-REPORT.md`).

### Чего проба НЕ ловит

Это важнее того, что она ловит, иначе на неё начнут полагаться как на матрицу.
`BALANCE_SAMPLE=1` сужает ОХВАТ, а не строгость: пороги, сравнения и ассерты те
же самые. Но охват сужен вчетверо по каждой оси сразу, и слепые пятна у неё
конкретные:

- **три зоны из двадцати.** Кривая ломается как раз на тех, что в выборку не
  попали, — это уже случалось.
- **два уровня из пяти и часов вчетверо меньше.** Всё, что видно только на
  длинном прогоне, она не увидит по построению: цена полного пути в убийствах,
  доля привалов, накопленная смертность.
- **один класс.** Контракт, который держится у Стража и разъехался у Изувера,
  проба пройдёт зелёной.
- **один сид.** Путь зависит от ранней рулетки находок и врёт на полтора часа
  в обе стороны; медиана по трём сидам считается только ночью.

Проба отсекает очевидное: сломанное на порядок она видит сразу. Заменить
матрицу она не может и не должна.

### Правила, которые из этого следуют

- **Быстрый набор — минимум, ниже которого опускаться нельзя никогда.** Ни одна
  правка не уходит в PR, не пройдя `npm run test`.
- **PR, трогающий `data/balance.ts`, кривые или формулы боя, обязан прогнать
  `npm run test:balance` ЦЕЛИКОМ и приложить таблицу в описание.**
- **Полная матрица — ОДИН раз перед созданием PR**, а не после каждой правки.

CI повторяет это разделение: типы, юниты, контент, баланс и снимки идут
ПАРАЛЛЕЛЬНЫМИ джобами, баланс и снимки — только если тронуто то, что их
касается (`src/lib/data/`, `src/lib/game/` для баланса; `src/lib/ui/`,
`src/lib/render2d/`, `App.svelte`, стили для снимков). Метка `full-checks`
на PR включает оба принудительно и переводит баланс на полную матрицу.
Ночью на `main` идёт `test:all` без выборок: красный ночной прогон означает,
что виноват один из мержей прошедшего дня.

СПИСОК ИСКЛЮЧЕНИЙ ЮНИТОВ ЖИВЁТ В ОДНОМ МЕСТЕ — в скрипте `test:unit`, и CI
зовёт именно его. Раньше список был выписан руками в трёх файлах и разъехался:
`power-budget.test.ts` попал в исключения только в `package.json`, и дорогой
тест шёл на каждом PR дважды.

## Архитектура

- `src/lib/game/` — логика: состояние, конвейер тика, формулы, лут, сейв, rng.
  Не знает про Svelte и рендер.
- `src/lib/data/` — статические данные и баланс в отдельных файлах
- `src/lib/types/` — типы и интерфейсы
- `src/lib/stores/` — Svelte stores, и их РОВНО ТРИ, с разными сроками жизни:
  - `stores/game.ts` — игровое состояние. Меняется ТОЛЬКО экшенами отсюда,
    лежит в сейве, переживает перезагрузку;
  - `stores/ui.ts` — экран: открытое меню, несомая вещь, развёрнутость
    «Деталей» (всё это «где я сейчас» — не хранится нигде) и настройки
    машины (текстовый режим, громкости — свой ключ localStorage, НЕ сейв).
    Там же карта меню: `MENU_IDS`, `MENU_SIDE`, `MENU_UNLOCK_LEVEL`;
  - `stores/telemetry.ts` — счётчики прогонов, к игре отношения не имеют.
- `src/lib/ui/` — Svelte-компоненты; весь текст для игрока живёт тут.
  `ui/tokens.css` — дизайн-токены, `ui/kit/` — примитивы без знания о
  состоянии. Подписи меню — `ui/menuText.ts`, названия осей — `ui/axisText.ts`,
  причины отказов — `ui/itemText.ts` и соседи: логика отдаёт КОД, слово
  подставляется здесь.
- `src/lib/render2d/` — двумерная боевая сцена: обычные элементы и
  CSS-трансформы. ТОЛЬКО ЧИТАЕТ состояние, не пишет в него (см. «Боевая
  сцена»).
- `src/lib/audio/` — звук; молчит до первого жеста игрока.
- `src/App.svelte` — сборка экрана: постоянная зона (кнопки · сцена ·
  кнопки, ряд действий, полоски) и одна панель открытого меню под ней.
  Единственный на игру слушатель Esc — тоже здесь.

  Отдельного `docs/ARCHITECTURE.md` в проекте нет: архитектура описана здесь,
  и второй копии заводить не надо — она разъедется.

## Железные правила

- Игровая логика НЕ знает о рендере и не трогает DOM. Платформенные API
  (requestAnimationFrame, localStorage, Date.now) в `game/` допустимы только через
  инжектируемые параметры с браузерными дефолтами — чтобы логика тестировалась в node.
- Состояние меняется ТОЛЬКО через экшены в `stores/game.ts`. Чистые функции и
  константы компоненты могут импортировать из `game/` и `data/` напрямую.
- `Decimal` обязателен для величин, растущих неограниченно: золото, урон, опыт, HP,
  уровни, счётчики покупок. НЕ применяется к вероятностям, весам рулетки,
  миллисекундам и служебным счётчикам — это обычные `number`.
- Никаких накопительных мутаций игровых величин: любое изменение статов выражается
  источником (уровень, количество апгрейдов, надетые предметы), из которого значение
  пересчитывается конвейером `game/stats.ts`. Итоговые статы меняются ТОЛЬКО
  добавлением/удалением модификатора — прямых полей урона в состоянии нет.
- НИКАКИХ ВЕТВЛЕНИЙ ПО КОНКРЕТНОМУ ID в логике: ни `if (талант === '...')`,
  ни `if (класс === '...')`, ни `if (зона === '...')`, ни по id умения, данжа
  или задания. Поведение включается ФЛАГОМ, а его числа лежат payload'ом
  в данных рядом с флагом. Иначе новая сущность требует правки логики —
  и правило «контент добавляется только данными» перестаёт работать.
  Держится grep-тестом по `src/lib/game` — `game/__tests__/rules.test.ts`.
  Он же держит ещё три правила отсюда: баланс только в `data/`, текст для
  игрока не в логике, случайность только через `rng.ts`. Исключения там
  перечислены поимённо и с причиной, и каждая проверка проверена на заведомо
  битом образце.
- Весь игровой баланс живёт в `src/lib/data` (общий — в `data/balance.ts`), а не
  хардкодом в логике или компонентах.
- ЛЮБАЯ новая сущность — зона, моб, предмет, талант, умение, данж, спрайт,
  иконка — добавляется ТОЛЬКО правкой в `src/lib/data` и обязана пройти
  `npm run content:check`. Проверка держит ссылки (данж → зона, талант →
  умение, спрайт → файл, иконка → symbol в спрайте), достижимость (в каждую
  зону есть путь, каждый предмет выпадает, до каждого таланта хватает очков),
  обязательные `id`/`name`/`icon` с уникальными id и диапазоны чисел.
  Схемы — `data/__tests__/schema.ts`, там же образцы битых данных, на которых
  проверено, что проверка вообще срабатывает. Новый ТИП данных — новая схема
  и строка в списке покрытия в `integrity.test.ts`.
- В `src/lib/game` нет текста для игрока — только структурированные события и коды;
  рендерит их UI.
- Любая случайность — только через `game/rng.ts` (`createRng`). `Math.random`
  в `src/lib/game` запрещён.
- Никаких `setInterval`/`setTimeout` внутри Svelte-компонентов для игровой логики —
  есть один общий игровой цикл.
- Формат сейва имеет `version`. Меняешь структуру сейва — поднимай версию, пиши функцию
  миграции и тест на загрузку сейва прошлой версии. Прогресс игрока терять нельзя.
- Один PR = одна фича. Не рефактори то, о чём не просили.
- Коммиты в стиле Conventional Commits (`feat:`, `fix:`, `chore:`). Никогда не коммить
  в `main` напрямую — только ветка + PR.
- Нетривиальные игровые формулы комментируй одной строкой: что считает и почему.

## Классы

- ОСНОВНОЙ КЛАСС ОДИН — СТРАЖ (мана), и до альфы он такой один. Готовность
  класса лежит в ДАННЫХ (`status` у `ClassDef` в `data/classes.ts`):
  `ready` — по нему считаются контракты, `preview` — выбирается и играется,
  но нигде не заявляется как сбалансированный. Изувер — `preview`.
- ВСЕ КОНТРАКТЫ БАЛАНСА — темп, цена боя, убийств на уровень, кран золота,
  обгон зон, цена схватки с боссом, смертность, прогон полного пути —
  СЧИТАЮТСЯ ПО ГОТОВЫМ КЛАССАМ с автокастом по умолчанию. Golden и эталон
  полного пути — тоже по Стражу (`DEFAULT_CLASS` — первый готовый класс).
  Двойных прогонов «по обоим классам» не возвращать: контракт, который
  обязан сходиться на недонастроенном классе, либо роняет прогон впустую,
  либо заставляет крутить баланс класса, который ещё не проектировали.
- Тесты превью-класса ОСТАЮТСЯ, но некритичны: `classIt(cls)` из
  `game/__tests__/class-set.ts` для `preview` превращает провал в
  `console.warn` с пометкой `[превью]` в имени теста. Список классов для
  прогона — `contractClasses(sample)`: готовые первыми, в выборке только
  первый готовый. Новый контракт по классам пишется ТОЛЬКО через них, а не
  через `it.each(CLASSES)`.
- Хотя бы один класс обязан быть `ready` — держит `content:check`: иначе не
  по кому считать контракты и некуда мигрировать старые сейвы.
- СИСТЕМА ОБЩАЯ, НАПОЛНЕНИЕ — ТОЛЬКО ГОТОВОМУ КЛАССУ. Четыре слота, порядок
  как приоритет и книга умений есть у обоих; одиннадцать умений — только у
  Стража, у Изувера их три и четвёртый слот пуст. Разрыв ВИДЕН намеренно, а
  не спрятан: что именно нужно Изуверу и почему разрыв допустим — отдельным
  документом `docs/BERSERKER-CATCHUP.md`.
- На экране выбора класса превью-класс НЕ ПРЯЧЕТСЯ: карточка на месте, с
  пометкой «В разработке» и одной строкой о том, что баланс не настроен.
  Текст, как и весь текст для игрока, живёт в UI (`ui/ClassPicker.svelte`).
- Когда Изувер будет настроен, переключение — одна правка данных:
  `status: 'ready'`. Логика и тесты про это не знают.

## Статы

- Конвейер `game/stats.ts` — единственный источник производных чисел. Порядок
  СТРОГО: `base -> +Σflat -> ×(1+Σpercent, аддитивно) -> ×Πmultiplier`.
- Четыре базовые характеристики — сила (урон), ловкость (скорость и криты),
  интеллект (мана), живучесть (здоровье) — обычные статы конвейера; их итоги
  сам конвейер разворачивает во вклады в производные статы плоскими
  модификаторами `attribute:<имя>` (ставки — в `data/balance.ts`). Прогрессия
  героя — предметы (у предмета есть УРОВЕНЬ, сила растёт от него линейно)
  и таланты, плюс небольшой прирост характеристик за уровень.
- Модификатор `kind: 'base'` ЗАМЕНЯЕТ дефолт из `data/balance.ts`, а не прибавляется.
  Контракт — ровно один base-источник на стат (оружие задаёт `weaponSpeed`); если
  их несколько, выигрывает последний в порядке `collectModifiers` (закреплено тестом).
- Скорость атаки — ДВЕ разные величины, имя `attackSpeed` запрещено:
  `weaponSpeed` — секунд между ударами (меньше = быстрее, база из `UNARMED`),
  `haste` — доля ускорения (больше = быстрее, старт 0).
- `swingTime = weaponSpeed / (1 + haste)` — производная, её нет среди `StatId`:
  модификатор на неё выдать нельзя, только на `weaponSpeed` или `haste`.
- Прогресс замаха хранится ДОЛЕЙ `0..1`, а не в миллисекундах: при смене оружия
  или haste доля сохраняется сама — ни сброса удара, ни мгновенного, ни эксплойта
  на переодевании. Пересчитывать её при изменении `swingTime` не нужно.
- У мобов оружия нет: в данных лежит `swingTime` напрямую.
- БРОНЯ (`armor`) — тоже обычный стат конвейера, но со своей нелинейной
  формулой на выходе; правила — в разделе «Броня».

## Броня

- БРОНЯ — ОБЫЧНЫЙ СТАТ КОНВЕЙЕРА (`armor`), целый, лежит на КАЖДОЙ части
  брони и на КАЖДОМ щите. Отдельным полем её никто не задаёт: генератор
  кладёт её общей константой (`ARMOR_BASE_DEFENSE`, `SHIELD_BASE_DEFENSE` в
  `data/items.ts`) и множит на ту же `power`, что и атрибуты. Своей кривой у
  брони нет — она разъехалась бы с остальным снаряжением на первой правке.
  Щиту досталось больше: он занимает руку, то есть стоит второго оружия.
- ФОРМУЛА НЕЛИНЕЙНАЯ (`armorReduction` в `game/combat.ts`, числа —
  `ARMOR_CURVE` в `data/balance.ts`):

  ```
  снижение = броня / (броня + K × уровень ГЕРОЯ),  потолок ARMOR_CURVE.maxReduction
  ```

  Нелинейность нарочно: у линейной каждая единица брони стоит одинаково, и
  сборка на броню упирается в сто процентов; здесь каждая следующая
  дешевеет, а потолок стоит ниже единицы — игра, где урон не проходит
  вовсе, перестаёт быть игрой.
- УРОВЕНЬ ГЕРОЯ В ЗНАМЕНАТЕЛЕ, А НЕ МОБА, И ЭТО НЕ МЕЛОЧЬ. Разницу уровней
  игра уже считает — `levelGapDamageMult`, пять уровней бесплатно, дальше
  +30 % за уровень. Возьми броня уровень моба, разница вошла бы в цену боя
  ДВАЖДЫ: моб на пять уровней старше бил бы и сильнее (штраф), и сквозь
  более тонкую броню (знаменатель). С уровнем героя броня становится мерой
  «насколько я одет ДЛЯ СВОЕГО УРОВНЯ», старая броня обесценивается сама по
  мере роста, а живучесть перестаёт зависеть от того, кто напротив, — и
  значит её можно показать игроку числом (см. «Две оси»).
- ЦЕЛЬ — 45–55 % ПОЛНЫМ АКТУАЛЬНЫМ КОМПЛЕКТОМ НА ЛЮБОМ УРОВНЕ, и под неё
  подобрана `K`. Замер по эталонному Стражу: 25 → 50.6 %, 55 → 49.0 %,
  85 → 48.5 %; коридор держится на всей лестнице, кривая садится на
  асимптоту 47–48 %. Полная таблица — `docs/UI-POLISH.md`.
- НОЛЬ НА ПЕРВОМ УРОВНЕ — НЕ ДЫРКА, А СТАРТОВЫЙ КОМПЛЕКТ: одно белое оружие
  и шесть пустых слотов. Первая же найденная часть брони поднимает снижение
  сразу к половине, и это самый заметный апгрейд в игре.
- БРОНЯ И ПЛОСКОЕ СНИЖЕНИЕ СКЛАДЫВАЮТСЯ МУЛЬТИПЛИКАТИВНО:
  `1 − (1−броня) × (1−damageReduction)` (`mitigationShare`). Сложением два
  источника легко переваливают за сто процентов, и урон становится
  отрицательным; умножением — никогда, каждый следующий режет ОСТАТОК.
- БЛОК В ЭТО ПРОИЗВЕДЕНИЕ НЕ ВХОДИТ: он снимает ФИКСИРОВАННУЮ величину и
  вычитается плоским числом уже из смягчённого удара. В этом половина смысла
  щита: против слабых ударов он хорош, против сильных обесценивается, а
  броня режет долю и не обесценивается никогда.
- УРОН МОБОВ ПЕРЕСЧИТАН ПОД БРОНЮ, и пропустить это нельзя: броня срезала
  половину входящего, а контракт цены боя стоит на прежнем месте.
  Двигается всё тем же ОДНИМ числом — `MONSTER_BASE.damage`; здоровье мобов
  не тронуто, контракт темпа 8–15 секунд держит именно оно. Полоса 1–5
  выведена из подорожания отдельным множителем `EARLY_HP_DISCOUNT`: у героя
  первых уровней брони ещё нет, и общий множитель пришёлся бы ему в полную
  силу.

## Экипировка

- Слоты — данные (`data/slots.ts`), не хардкод в логике. Шаблоны предметов —
  `data/items.ts`.
- СТАРТОВЫЙ КОМПЛЕКТ — ОДНО БЕЛОЕ ОРУЖИЕ, шесть слотов пусты. Тир лежит в
  данных класса (`rarity` у `StartingItem`), а не в коде. Полный редкий
  комплект прежней версии не давал запуститься главной петле игры: почти
  любая находка была хуже подарка, и значок «Апгрейд» не загорался часами.
- ПУСТОЙ СЛОТ — ЭТО НОЛЬ, и порог апгрейда для него другой: вещь не обязана
  оценку ПОДНЯТЬ, ей достаточно её не уронить. Правило появилось, когда мера
  «лучше» была одна — убийств в секунду, — и панцирь на голое место её не
  двигал вовсе. Осей теперь две, и панцирь двигает живучесть честно; правило
  всё равно остаётся, потому что вещь без прибавки к обеим осям (украшение с
  одним стат-мусором) на пустое место всё-таки лучше пустоты.
- НА ВЫПАДАЮЩИХ И КОВАНЫХ ВЕЩАХ ТОЛЬКО ПЛОСКИЕ ПРИБАВКИ. Процент считается
  от суммы конвейера, то есть от остальной экипировки: такой предмет нельзя
  оценить сам по себе, а сравнение находок поштучное. И он не растёт ни от
  уровня вещи, ни от тира — множитель силы умножает плоское, а проценту
  умножать нечего. Проценты живут в зачарованиях, талантах и зельях.
  Держится проверкой контента.
- ЧИСЛА НА ПРЕДМЕТЕ ЦЕЛЫЕ ТАМ, ГДЕ ОНИ СЧИТАЮТСЯ ШТУКАМИ. Граница —
  `ITEM_STAT_GRAIN` в `data/items.ts`, `Record<StatId, 'whole' | 'fraction'>`:
  новая характеристика не пройдёт проверку типов, пока про неё не решат.
  `'whole'` — атрибуты, урон оружия, сила атаки, запасы, БРОНЯ, сила блока;
  `'fraction'` — доли (шанс крита и блока, ускорение, снижение урона,
  множитель крита, сила левой руки, порог привала), секунды (скорость
  оружия, пауза регена, длина привала) и величины в секунду (реген).
  Округление идёт НА ГЕНЕРАЦИИ, в одной точке (`grained` в `game/loot.ts`,
  через неё проходят находка, ковка и стартовый комплект), а не на
  отображении: карточка обязана показывать то же, что считает бой.
  К БЛИЖАЙШЕМУ, а не вниз — вниз забирало бы в среднем полединицы с каждой
  строки; замер сдвига суммы по сетке «шаблон × тир × уровень» — 0.006 %.
- КОНКРЕТНАЯ ВЕЩЬ — ЦЕЛАЯ, МАТОЖИДАНИЕ — НЕПРЕРЫВНОЕ. Единственное место без
  округления — `averageArmorMods`: там считается не вещь, а среднее по
  популяции вещей. Ступенька в эталоне запрещена тем же доводом, что и
  `floor`/`ceil` в `farmCycle` (см. «ОЦЕНКА — ДОЛГОСРОЧНОЕ СРЕДНЕЕ»):
  округлённый эталон стал бы ступенчатой функцией уровня вещей, и контракты,
  которые меряются по лестнице уровней, начали бы прыгать на границах.
  Расхождение с настоящей популяцией при этом меньше половины единицы на
  стат. Оружие и щит эталона округляются как все: это КОНКРЕТНЫЕ вещи и в
  модели тоже.
- У всего, что идёт в руки, есть ХВАТ (`grip` в шаблоне): `'one'` — в любую
  руку, `'two'` — обе руки, `'shield'` — только вторая. Одно поле, а не два
  флага: щитом и оружием одновременно быть нельзя. Хват берётся ИЗ ШАБЛОНА
  и отдельным броском не разыгрывается; проверяется схемой в `content:check`.
- Правила хвата живут в `game/equipment.ts` (`equipStatus`) и возвращают КОД
  отказа — `two-handed-needs-both`, `shield-offhand-only`,
  `occupied-by-two-handed`. Текст причины рендерит UI, как у умений.
  Двуручное само снимает вторую руку В СУМКУ; сумка полна — отказ кодом,
  а не молчаливая потеря предмета.
- У предмета есть `slot` и `mods` — массив модификаторов в формате `stats.ts`.
  Никаких «прибавок к урону» отдельным полем: предмет действует ТОЛЬКО через
  конвейер статов.
- Главный атрибут брони К СЛОТУ НЕ ПРИВЯЗАН: его разыгрывает лут
  (`ARMOR_ATTRIBUTES`, ровные веса), у кованого он задан в данных рецепта.
  Эталон прогона берёт матожидание (`averageArmorMods`) — четверть бюджета
  в каждый атрибут.
- Оружие задаёт БАЗУ боя: `weaponSpeed`, `weaponDamageMin`, `weaponDamageMax`
  тремя модификаторами `kind: 'base'` с `source: 'equipment:weapon'`. Сняли —
  значения вернулись к `UNARMED` из `data/balance.ts`. Побочные статы оружия
  (сила атаки, крит, haste) — ОБЫЧНЫЕ модификаторы, не base.
- Надетый предмет продать нельзя — сперва снять (`sellItem` проверяет явно).
- КУКЛА — АНАТОМИЧЕСКАЯ СЕТКА ЗНАЧКОВ, А НЕ СТОЛБИК КАРТОЧЕК. Голова сверху,
  талисман сбоку от неё, вниз по центру грудь и ноги, кисти сбоку, обе руки в
  нижнем ряду. В ячейке значок слота и уровень вещи — и больше ничего.
  Карточек было семь, и в каждой лежало полное описание предмета: имя, ярлык
  редкости, хват, зачарование, список модификаторов. На телефоне это четыре
  десятка строк, то есть сумка уезжала под сгиб — и переодевание, ради
  которого кукла и существует, шло вслепую.
- МЕСТО СЛОТА НА КУКЛЕ — ДАННЫМИ (`SLOT_CELL` в `data/slots.ts`), как и его
  иконка. Раскладка анатомическая, из порядка `SLOT_IDS` она не выводится, а
  расставлять её условиями `if (slot === 'head')` в компоненте значит завести
  восьмое такое условие на восьмом слоте.
- ДВУРУЧНОЕ ЗАНИМАЕТ ОБЕ ЯЧЕЙКИ РУК ВИДИМО: руки стоят соседями (ряд 4), и
  пара рисуется одним широким блоком в цвете оружия (`join` у `IconSlot`).
  Но ЯЧЕЕК ПО-ПРЕЖНЕМУ ДВЕ, и сливать их в одну нельзя: у второй свой фокус,
  свой бросок и своя строка отказа — слот занят, а не исчез.
- ОПИСАНИЕ НАДЕТОГО — ОКНОМ У КУРСОРА (`ui/ItemTip.svelte`), а не в ячейке.
  Это НЕ `ItemCompare` и сливать их не надо: то окно отвечает на вопрос «что
  изменится, если надеть», и у надетой вещи ответ на него — нули. Границы
  экрана оба окна считают одной функцией (`ui/tipPlace.ts`): два окна у
  одного курсора обязаны переворачиваться одинаково.
- ХВАТ НАЗЫВАЕТСЯ СЛОВОМ В ОБОИХ ОКНАХ. Одноручное оружие от двуручного
  отличается вдвое большим уроном и вдвое меньшей частотой — то есть всей
  сборкой, — а узнать это можно было только надев. Подпись строит общий
  `itemSlotLabel`: двух ответов на один вопрос быть не должно.
- ВСЁ, ЧТО ПОЯВЛЯЕТСЯ И ПРОПАДАЕТ, СТОИТ ПОД СЕТКОЙ, А НЕ НАД НЕЙ — строка
  «несёшь», причины отказа, подсказка осей. Строка «несёшь» жила выше куклы и
  двигала её ровно в тот момент, когда игрок брал вещь в руку: сетка съезжала
  на высоту строки, второе нажатие приходилось мимо ячейки, и двойной щелчок
  по надетому переставал работать вовсе. Ячейка теперь мелкая, и промах в
  тридцать пикселей стоит целого слота.
- ПУТЕЙ НАДЕТЬ НАХОДКУ ТРИ, И ОНИ НЕ ВЗАИМОЗАМЕНЯЕМЫ: перетаскивание мышью,
  «нажал вещь → нажал подсвеченный слот» (единственный на тач-экране, где
  HTML5-перетаскивания нет вовсе) и долгое нажатие/двойной щелчок — «надеть
  сразу». Плюс клавиатура: Tab до ячейки, Enter или пробел. Решает «можно ли
  сюда» ОДНА функция на все пути — `ui/dropTarget.ts`; своей проверки у пути
  быть не должно, иначе они разъедутся на первой правке правил хвата.
- ПОДХОДЯЩИЙ СЛОТ ПОДСВЕЧИВАЕТСЯ, НЕПОДХОДЯЩИЕ ТУШАТСЯ. Подходит ровно один —
  тот, в который вещь бросил лут: «положи куда хочешь» было бы обещанием,
  которого игра не держит (менять слот предмета она не умеет).
- «ПОДХОДИТ» И «МОЖНО ПРЯМО СЕЙЧАС» — РАЗНЫЕ ВЕЩИ. Слот, который подходит, но
  занят или запрещён хватом, остаётся ПОДСВЕЧЕННЫМ и получает СТРОКУ С
  ПРИЧИНОЙ — до попытки, а не после неё. Коды приходят из логики
  (`two-handed-needs-both`, `shield-offhand-only`, `occupied-by-two-handed`,
  `inventory-full`), слова живут в `ui/itemText.ts`. Сама строка стоит ПОД
  СЕТКОЙ и называет слот: в квадрат со значком предложение не помещается.
  «Снять мешает полная сумка» — одна причина на всё надетое, поэтому и строка
  одна: семь одинаковых строк это не семь причин.
- НАДЕТОЕ, БРОШЕННОЕ В СУМКУ, СНИМАЕТСЯ. Перетаскивание работает в обе
  стороны — иначе на одно действие пришлось бы два разных жеста.
- КНОПОК «НАДЕТЬ» И «СНЯТЬ» НЕТ НИ В СУМКЕ, НИ НА КУКЛЕ. Каждая была
  ЧЕТВЁРТЫМ способом сделать то же самое: надеть можно тремя жестами, снять —
  тремя, и все шесть держатся тестами в `tests/doll.spec.ts`. Кнопка рядом с
  жестом читается как «а жест, наверное, не работает», и на ячейку значка
  размером в палец она всё равно не помещается.
- СУМКА — СЕТКА ЗНАЧКОВ, А НЕ СТОЛБИК КАРТОЧЕК. В ячейке значок слота,
  уровень вещи и метка апгрейда — и больше ничего. Полтора десятка карточек
  со списком модификаторов не помещались ни на телефон, ни в ширину меню, и
  находку приходилось ИСКАТЬ ЧТЕНИЕМ. Ячейка квадратная, и это проверяется:
  сетка значков обязана оставаться сеткой.
- ИМЯ, СТАТЫ И ДЕЙСТВИЯ — У ВЫБРАННОЙ ВЕЩИ, одной карточкой под сеткой
  (`[data-chosen]`). Там же «Распылить» и вторая «Продать»: на телефоне это
  единственное место, где вещь можно ПРОЧИТАТЬ перед тем, как решить.
- ПРОДАЖА ЕСТЬ И В УГЛУ САМОГО ЗНАЧКА, справа снизу, — и это не четвёртая
  кнопка к трём жестам, а та же одна, придвинутая к находке. Разобрать полную
  сумку через карточку выбранного значит выбрать вещь, отвести взгляд вниз,
  прицелиться в кнопку и вернуться к сетке, и так полтора десятка раз: мусора
  в сумке больше, чем находок, и дорога до кнопки стоила дороже решения.
  Кнопка приглушена до наведения: полтора десятка ярких монет перебили бы
  метку апгрейда — единственное, ради чего в сетку и смотрят. Нажатие мимо сетки снимает
  выбор и вместе с ним подсветку слотов — вещь не остаётся висеть в руке
  после того, как игрок ушёл смотреть другое.
- Esc СНИМАЕТ БЛИЖАЙШЕЕ: сперва вещь из руки, и только если руки пусты —
  меню. Одно нажатие не должно и ронять находку, и закрывать экран, на
  котором её выбирали.
- Сравнение предметов — только по производным конвейера боя, никогда по
  сумме статов. Каких именно производных и почему их две — раздел «Две оси».
- ПОДСКАЗКА СРАВНЕНИЯ ПОКАЗЫВАЕТ ОБЕ СТРОКИ ВСЕГДА, со знаком и процентом.
  Приоритет решает, что ПОДСВЕТИТЬ, а не что показать. Сам приоритет, его
  три положения и правило «лучше хоть по одной оси» — раздел «Две оси».
- ОЦЕНКА — ДОЛГОСРОЧНОЕ СРЕДНЕЕ, А НЕ ОДИН ЦИКЛ. `estimateCombatRate`
  описывает сотни боёв за час, поэтому целых чисел одного цикла в ней нет:
  удары на моба, ответные удары за бой и бои до привала — дробные
  матожидания («целое, усреднённое по фазе» = дробное плюс половина), а
  смерть в цикле — вероятность, а не флаг (`farmCycle`, разброс цены боя
  `FIGHT_COST_SPREAD`). Прежние `floor`/`ceil` делали метрику ступенчатой:
  единица силы атаки перекидывала цикл с привала на смерть и роняла темп
  убийств втрое, а сравнение предметов выбирало худшее (откат `4a000e4`).
  Держится тестом `rate-continuity.test.ts`: по мелкой сетке каждого стата
  силы `killsPerSecond` не убывает, а шаг между соседями не больше
  `RATE_CONTINUITY_MAX_STEP` от наибольшего. Новый `floor`/`ceil` в
  `rawRate` или `farmCycle` — это регрессия, а не уточнение.

## Две оси

- ОСЕЙ РОВНО ДВЕ, И ОБЕ СЧИТАЮТСЯ ПРОТИВ ЭТАЛОННОГО ПРОТИВНИКА — моба
  уровня героя, построенного той же `buildMonster` и не принадлежащего ни
  одной зоне (`REFERENCE_ARCHETYPE` в `data/monsters.ts`). Считает их
  `axesOf` в `game/equipment.ts`:
  - `damage` — УРОН В СЕКУНДУ по эталону, с перебоем добивающего удара
    (`sustainedDamagePerSecond` из `estimateCombatRate`): чистая пропускная
    способность, без аптайма, привалов и смертей;
  - `survival` — ЖИВУЧЕСТЬ: сколько урона герой держит за одну типичную
    схватку, `(запас + реген × TYPICAL_FIGHT_SEC) / (1 − смягчение)`. Число
    абсолютное, в единицах здоровья.
- У ОБЕИХ ОСЕЙ БОЛЬШЕ — ЛУЧШЕ, и переворачивать внутри нечего. Прежняя ось
  выживания мерила СНИЖЕНИЕ цены боя, то есть у неё «меньше — лучше», и знак
  приходилось разворачивать в каждой точке, где число показывают.
- ГРАНИЦА, КОТОРУЮ НЕЛЬЗЯ РАЗМЫВАТЬ: **две оси — для ИГРОКА и для решений об
  экипировке; `estimateCombatRate` целиком и контракт цены боя — МОДЕЛЬ, по
  ней считаются прогноз зоны, оффлайн, прогон баланса и тесты.** Оси обязаны
  быть простыми, устойчивыми и НЕ ЗАВИСЕТЬ ОТ ТОГО, ГДЕ ГЕРОЙ СТОИТ; модель
  обязана быть точной. Смешаешь — и одна и та же вещь начнёт читаться
  по-разному в двух шагах пути. Правило записано в шапке `data/upgrade.ts`.
- ПОЧЕМУ ЭТАЛОН, А НЕ МОБЫ ЗОНЫ. Пока оси считались по трём мобам текущей
  зоны, одна и та же вещь была апгрейдом на лугу и лишней в пещере, а при
  переезде числа в карточке героя прыгали без единого изменения в
  снаряжении. Эталон уровня героя убирает это по построению — и он же
  делает живучесть показуемым числом.
- ВТОРАЯ ОСЬ ПОЯВИЛАСЬ, ПОТОМУ ЧТО ПЕРВАЯ НЕ ВИДЕЛА ЗАЩИТУ. Живучесть входила
  в убийства в секунду только через аптайм, а в зоне, где герой не гибнет,
  аптайм равен единице: панцирь не двигал оценку вовсе, двуручное всегда
  било связку со щитом, и защитные ветки талантов отставали в полтора раза.
  Это было третье появление одной и той же слепой зоны.
- ДВА ЧИСЛА КРУПНО В КАРТОЧКЕ ГЕРОЯ — ЭТИ ЖЕ ДВА. Игрок обязан видеть ту же
  пару, по которой игра называет находку апгрейдом; третьего числа на видном
  месте нет, остальное — под «Деталями».
- ПОДСКАЗКА СРАВНЕНИЯ ПОКАЗЫВАЕТ ОБЕ СТРОКИ ВСЕГДА, со знаком и процентом.
  Приоритет решает, что ПОДСВЕТИТЬ, а не что показать. Названия и
  форматирование — один модуль на игру (`ui/axisText.ts`): двумя копиями в
  компонентах они разъехались бы, и игрок читал бы два разных ответа на один
  вопрос.
- ПРИОРИТЕТ ИГРОКА — три положения (`data/upgrade.ts`): урон, выживание,
  баланс; по умолчанию БАЛАНС, живёт в сейве. Правило одно на все три:
  апгрейд — если лучше хотя бы по одной из осей приоритета, лишнее — если не
  лучше ни по одной. Отсюда «баланс — лишнее только если хуже по обеим».
  Ветвлений по конкретному положению в логике нет: оси лежат в
  `UPGRADE_RULES`.
- ЖЕЛЕЗНОЕ ПРАВИЛО СИЛЬНЕЕ ПРИОРИТЕТА: находка, лучшая хоть по одной оси,
  при полной сумке не продаётся и не распыляется — она вытесняет худшее
  (`betterOnAnyAxis`, вызывается БЕЗ приоритета). Игрок, поставивший «урон»,
  просил не звать панцирь апгрейдом, а не выбрасывать его.
- МОДЕЛЬ ИГРОКА В ПРОГОНЕ — ЭТО ПРИБОР, И МЕРИТ ОНА ОДНИМ ЧИСЛОМ. Порядок
  «лучше» по двум осям ЧАСТИЧНЫЙ: вещь, меняющая урон на живучесть, и
  обратная считаются апгрейдами друг над другом, и модель, ранжирующая по
  «лучше хоть по одной», переставляет их бесконечно. Поэтому `equipUpgrades`
  в `game/simulate.ts` выбирает по СКАЛЯРУ — среднему темпу убийств по мобам
  текущей зоны (`modelRate`), — а две оси остаются там, где они и нужны: у
  игрока. Это разные вопросы: «что показать человеку» и «что надел бы
  идеальный игрок».

## Умения

- Умения — данные (`data/abilities.ts`): `manaCost`, `cooldown`,
  `weaponDamagePercent`, `triggersGcd`, `unlockLevel`, опциональный `effect`.
- СЛОТОВ ЧЕТЫРЕ (`ABILITY_SLOTS`), А УМЕНИЙ У ГОТОВОГО КЛАССА ОДИННАДЦАТЬ.
  Выбор четырёх из одиннадцати — единственный рычаг игрока над ротацией, и
  он же смысл всего набора: умения ДОЛЖНЫ БЫТЬ РАЗНЫМИ, а не сильнее.
- ПОРЯДОК СЛОТОВ И ЕСТЬ ПРИОРИТЕТ АВТОКАСТА: первый слот жмётся первым.
  Числа приоритета в состоянии НЕТ — оно разъехалось бы с рядом на первой же
  перестановке. Ряд лежит в сейве полем `abilitySlots`, `null` — пустой слот.
- НЕПОЛОЖЕННОЕ В РЯД УМЕНИЕ НЕ УЧАСТВУЕТ НИ В ЧЁМ — ни в автокасте, ни в
  ручной игре, ни в модели боя. Кнопки у него на экране нет, и обещать в
  расчёте то, чего игрок нажать не может, нельзя.
- ОТКАТЫ ЖИВУТ НА УМЕНИИ, А НЕ НА СЛОТЕ. Перестановка меняет местами ИМЕНА, а
  `abilityCooldownsMs` не трогает: иначе смена четвёрки стала бы бесплатным
  сбросом откатов, и автокаст с прогоном нашли бы это в первый же час.
- СЕТКА РАЗБЛОКИРОВОК БЕЗ ДЫР: первый уровень плюс каждый второй до
  двадцатого (`ABILITY_UNLOCK_GRID` в `data/balance.ts`), на каждой ступени
  ровно одно умение, выше двадцатого не заперто ничего. Дальше восемьдесят
  уровней БЕЗ НОВЫХ КНОПОК: там игру меняют таланты. Сетку держит
  `content:check` — но ТОЛЬКО у готовых классов, и причина исключения названа
  прямо в коде проверки.
- Запертая кнопка ВИДНА в ряду с уровнем открытия, автокаст запертые
  пропускает. Слоты по умолчанию уровня не смотрят: три пустых квадрата
  вместо трёх обещаний — хуже.
- Урон умения — ДОЛЯ УДАРА ОРУЖИЯ (`weaponDamagePercent`), а не множитель
  к силе атаки: иначе умения перестанут масштабироваться от оружия. Считает
  их та же `rollSwing` из `combat.ts` — своей формулы у умений нет.
- Два типа. `instant` бьёт сразу, тратит GCD и НЕ трогает прогресс замаха.
  `onNextSwing` встаёт в очередь и заменяет следующую автоатаку: GCD не
  тратит, отменяется повторным нажатием, мана списывается В МОМЕНТ УДАРА.
  Одновременно в очереди только одно `onNextSwing`.
- Кулдауны и GCD идут ИГРОВЫМ временем (тем же `dtMs`), поэтому множитель
  скорости из отладочной панели ускоряет и их.
- Каждый отказ — отдельный код (`locked`/`dead`/`cooldown`/`gcd`/`no-mana`/
  `no-combo`/`target-healthy`) из `abilityStatus`; текст причины рендерит UI.
- ПОВЕДЕНИЕ ЗАДАЁТСЯ ФЛАГОМ С PAYLOAD'ом, и флагов этих семь: `heal`,
  `weaken`, `detonate`, `absorb`, `execute`, `brand`, `freeCasts`, `stance`.
  Ни одной ветки по id: логика читает флаг, числа берёт из его payload, а
  связка между умениями описана полем `combo` — по нему интерфейс и говорит
  игроку, что «Разрыв» без «Рваной раны» не работает.
- УМЕНИЕ, КОТОРОЕ АВТОКАСТ НЕ УМЕЕТ ПРИМЕНЯТЬ РАЗУМНО, — ПЛОХОЕ УМЕНИЕ В
  ИДЛ-ИГРЕ, даже если в руках оно сильное. Поэтому у ситуативных умений
  порог лежит В ДАННЫХ: добивание отказывает кодом, пока цель цела, а клеймо
  автокаст не вешает на моба ниже `autocastAboveHpShare` — на умирающем оно
  не окупается, а ресурс тратит. Руками игрок волен жать что угодно.
- ЛЕЧЕНИЕ — ФЛАГ `heal` С PAYLOAD'ом в данных умения, а не тип и не ветка
  по id: `maxHpShare` (доля МАКСИМАЛЬНОГО запаса — плоское число устарело
  бы к тридцатому уровню) и `autocastBelowHpShare` (порог автокаста). Такое
  умение бьёт нулём (`weaponDamagePercent: 0`), только мгновенное, платит
  как все и считается в `abilityCasts`. Держит схема: боевое умение обязано
  бить, лечащее — не бить. У Стража это «Заживление ран» с шестого уровня:
  мана без лечения была бы яростью под другим именем — тратить её было
  бы не на что, кроме урона.
- Очередь и наложенные эффекты живут на КОНКРЕТНОМ мобе: его смерть, респаун,
  смерть героя и загрузка сейва их снимают. Это относится и к меткам:
  кровотечение, ослабление и клеймо висят на мобе, щит и стойка — на герое,
  и ни одна из них в сейв не пишется: после загрузки нет ни того моба, ни той
  секунды боя.
- ПОРЯДОК СМЯГЧЕНИЯ ВХОДЯЩЕГО ФИКСИРОВАН: броня и плоское снижение (см.
  «Броня») → блок снимает фиксированную величину → стойка режет долю
  оставшегося → щит съедает то, что дошло бы до полоски. Каждый шаг работает
  с ОСТАТКОМ, и ни один не может увести урон в минус.
- НАБОР ДОБАВЛЯЕТСЯ КАК ПЕРЕРАСПРЕДЕЛЕНИЕ СИЛЫ, А НЕ КАК ПРИБАВКА. Сила
  ЛУЧШЕЙ ЧЕТВЁРКИ — строка бюджета (`POWER_BUDGET.multipliers.abilities`), и
  меряет её полный перебор всех сочетаний в
  `game/__tests__/balance-abilities.test.ts`. Там же жёсткое правило: каждое
  умение обязано входить хотя бы в одну выигравшую четвёрку хотя бы на одном
  срезе. Умение, не входящее никуда, — украшение, и чинить надо УМЕНИЕ.

## Данжи

- Данж — данные (`data/dungeons.ts`): вход из конкретной зоны,
  `unlockRequirement`, цепочка боссов в ФИКСИРОВАННОМ порядке и `opensZoneIds`
  — РОВНО ДВЕ зоны, которые открывает первое прохождение.
- ЦЕНА СХВАТКИ С БОССОМ — ОКОЛО 80% ЗАПАСА героя, хорошо одетого для своего
  уровня; коридор контракта 60–95 %. Свежий замер тиком по всем восьми
  данжам: 63–92 %, в среднем 78. Это отдельный контракт, рядом с контрактом
  цены обычного боя, и держится он тестом на настоящем тике.
- МЕЖДУ БОССАМИ ЕСТЬ ПРИВАЛ, и он несёт предыдущий пункт: три схватки по 80%
  на одном запасе не проходятся никак. Каждая ступень цепочки начинается с
  полной полоски, поэтому и мерить цепочку надо схваткой, а не суммой.
  После ПОСЛЕДНЕГО босса привала нет — отдыхать не от чего, герой выходит.
  На привале СТОИТ СЧЁТЧИК ЯРОСТИ и не выходит следующий босс: иначе герой
  возвращался бы к противнику, разъярённому на всю длину отсидки.
- УРОН БОССА ПАДАЕТ ОТ ПЕРВОГО К ТРЕТЬЕМУ (`CHAIN` в `data/dungeons.ts`:
  1.86 → 1.28 → 1.00; тир домножает все три разом), и это арифметика равной
  цены, а не «третий слабее»: запас HP растёт по цепочке в 1.7 раза
  (3.6 → 4.6 → 6.0), схватка ровно во столько же длиннее, значит урон в
  секунду обязан упасть. Опасность третьего босса — в ДЛИНЕ боя: отметка
  ярости у него ближе к пределу.
- БРОНЯ ПОТРЕБОВАЛА ПЕРЕСЧЁТА И ЗДЕСЬ, и не тем множителем, что у обычных
  мобов. Цена схватки — «входящий минус лечение», а лечение от подорожания
  входящего не растёт, поэтому общая прибавка урона легла на разность и
  схватка подорожала сверх плана: с прежними множителями замер дал 63–97 %,
  и второй тир вышел за верхнюю границу. Множители срезаны на 5 %
  (1.96/1.35/1.05 → 1.86/1.28/1.00) — скан обоих вариантов лежит рядом с
  самими числами.
- ЦЕНА СХВАТКИ СЧИТАЕТСЯ С ЛЕЧЕНИЕМ. С появлением лечения у Стража
  множители урона боссов подняты на треть и больше: за схватку автокаст
  лечится два-четыре раза (откат 12 с), и с прежними числами она стоила
  31–63 % вместо ~80. Без лечения босс теперь стоит больше запаса — данж для
  Стража требует лечения, и это осознанно (числа и скан — `data/dungeons.ts`).
- ДАНЖ — ЖЁСТКИЕ ВОРОТА, и требовательность растёт по тиру: первый берётся
  82% доступной экипировки, восьмой требует 96% (`requiredGearShare` = 80 +
  2×тир). Проверяется В ОБЕ СТОРОНЫ: с положенной долей цепочка проходится,
  с долей на 15 пунктов ниже — нет. Односторонняя проверка пропустила бы
  данж, который проходится всегда, то есть перестал быть воротами.
  Лестница ВЫСОКАЯ И УЗКАЯ (было 60-95%) именно из-за цены схватки: если
  босс снимает 80% с хорошо одетого, то плохо одетого он снимает целиком.
- Босс — не отдельная сущность: та же `buildMonster`, что и у мобов, только
  роль умножена на `hpMult`/`damageMult`/`goldMult`/`xpMult`. Своей формулы
  у боссов нет.
- Лут босса — свой пул (`loot.slots` + `minRarity`), качество растёт от
  первого босса к третьему. Падает целиком, а не по общему шансу дропа.
- Ярость: после `enrageAfterSec` урон растёт на `ENRAGE_GROWTH` каждые
  `ENRAGE_STEP_SEC`. Это проверка на урон в секунду и ЗАЩЁЛКА ДЛЯ СИЛЬНО
  ОТСТАВШИХ, а не главный убийца. Пока схватка стоила десятой доли запаса,
  обычные удары не убивали никого и дожимала только отметка; при цене в 80%
  герой, который тянет схватку в полтора раза дольше, не доживает до отметки
  и без неё. Не пытайтесь вернуть «обычные удары герой переживает всегда» —
  это прямо противоречит цене схватки.
- Смерть внутри выкидывает наружу и стирает прогресс цепочки; лут за уже
  убитых боссов остаётся. Добровольный выход — то же самое.
- Первое полное прохождение поднимает флаг в `dungeonsCleared` — РОВНО один
  раз — и даёт постоянный бонус к опыту.
- Цепочка боссов сама себя не проходит: оффлайн-агрегат внутри забега не
  считается. Что происходит с забегом при загрузке сейва — ниже, общим
  правилом для всего закрытого контента.

## Храм испытаний

- Храм КОНЕЧЕН: `floors` в `data/temple.ts`. Без потолка «полная зачистка»
  недостижима, а с ней недостижимы и награда за неё, и честное «награды
  исчерпаны» на входе.
- КУЛДАУНА НЕТ. Заходить можно сколько угодно; фарм закрыт не запретом, а
  построением: платят только этажи ВЫШЕ рекорда, а рекорд нельзя побить
  дважды. Рекорд — максимальный ПОЛНОСТЬЮ пройденный этаж, лежит в сейве.
- КРИВУЮ СЛОЖНОСТИ ЗАДАЁТ УРОВЕНЬ ЭТАЖА, а не уровень героя. Боец этажа N —
  моб уровня `templeFloorLevel(N)` = 66 + 2N с потолком `LEVEL_CAP`; ставки
  волны остались только на здоровье. Раньше боец брал уровень ГЕРОЯ, и храм
  был ровным: 70 → 5 этажей, 90 → 5, 100 → 5-7, то есть полная зачистка
  недостижима в принципе. Стеной работает общее правило мира
  (`levelGapDamageMult`), а не своя механика храма. Замер по трём сидам:
  **70 → 5 этажей, 90 → 15, 100 → 20**; решение владельца — «примерно
  5 / 15 / 20». Держится `balance-temple.test.ts` двусторонне: одетый по
  контракту ворот данжей доходит до ожидаемого ±1, недоодетый на 15 пунктов —
  строго мельче.
- Награда за этаж — пыль и золото, числа в данных (`floorReward`), растут по
  этажам. За полную зачистку СВЕРХУ и ровно один раз: токен для преквеста
  рейда и уникальный рецепт; повторная зачистка их не дублирует (флаг
  `templeCleared`, а не «рекорд равен потолку»).
- КОПИЛКА ЗАБЕГА ВИДНА ДО ЕГО КОНЦА. `pendingTempleReward` считает ту же
  арифметику, что и `finishTempleRun` (второй копии правила «платят только
  этажи выше рекорда» нет), но состояние не меняет: HUD показывает ею, что
  игрок заберёт, выйдя сам, и что потеряет, закрыв вкладку.
- СМЕРТЬ ЗАСЧИТЫВАЕТСЯ. Это завершение забега с результатом: этаж, на котором
  героя добили, пройденным не считается (его отмечает смерть БОЙЦА), а все
  этажи под ним оплачиваются и поднимают рекорд. Добровольный выход — то же
  самое.
- ПРЕРЫВАНИЕ НЕ ЗАСЧИТЫВАЕТСЯ, и это ДРУГОЙ путь. Закрытая вкладка
  расформировывает забег общим правилом (`resumeOutside`): рекорд не меняется,
  награды не выдаются. Разводит их последний аргумент `leaveTemple(credit)`.
  Пойди смерть по ветке прерывания — погибнуть стало бы не дороже, чем
  закрыть вкладку, и риск смерти вместе с привалом потерял бы смысл.
- НАГРАДА ЗА ХРАМ — ЭТАЖИ, А НЕ МОБЫ. Бойцы храма не дают ни опыта, ни
  золота, и лут внутри не падает. Замер до правки: храм на семидесятом
  уровне давал 386 578 опыта в час против 249 266 в подходящей зоне и больше
  убийств, то есть и бросков лута. Кулдауна нет — храм стал бы лучшей фермой
  в игре.

## Прерванные забеги

Общее правило для ВСЕГО закрытого контента: данжа, храма и будущего рейда.
Отдельной ветки на каждую активность быть не должно — правило держится в
одной точке (`resumeOutside` в `game/save.ts`).

- Прерванный забег ПРИ ЗАГРУЗКЕ СЕЙВА расформировывается: прогресс цепочки
  сброшен, лут за уже убитых боссов остаётся, герой выходит наружу в
  подходящую по уровню зону, и оффлайн начисляется ПО НЕЙ. Закрыв игру в
  любой момент, игрок не должен возвращаться к пустому экрану.
- Сама попытка при этом НЕ продолжается в оффлайне и НЕ засчитывается —
  забег придётся начать заново. Это ДВА РАЗНЫХ СВОЙСТВА, и путать их нельзя:
  первое — про то, что время не пропало; второе — про то, что данжи не
  проходятся закрытой вкладкой.
- Зону выхода выбирает одна детерминированная функция (`offlineZone` в
  `game/zones.ts`), строго в этом порядке: последняя выжитая, если её мобы
  в пределах `gap <= 5`; иначе самая высокая открытая зона, где герой не
  гибнет и мобы не отстали; иначе безопасная.
- Модалка возврата НАЗЫВАЕТ это вслух: из чего вышел и по какой зоне
  начислено. Молча пропавшая цепочка читается как потеря прогресса.
- При входе в закрытую активность UI предупреждает одной строкой
  (`ui/runText.ts`), что закрытая вкладка прервёт забег, но оффлайн будет
  начислен. Строка снимает главный страх и стоит копейки.

## Таланты

- Дерево — данные (`data/talents.ts`): у каждого класса три ветки по 13
  этажей глубиной `BRANCH_DEPTH` = 61 очко; у таланта `branch`, `row`,
  `maxRank`, `requiredPointsInBranch` и `effect`.
- Эффект бывает ДВУХ видов и только двух: массив модификаторов конвейера
  статов (`source: 'talent:<id>'`, значение множится на ранг) либо ФЛАГ,
  включающий поведение. Ни одного `if (талант === '...')` в логике: флаг
  описан в данных вместе со своим payload.
- Очко за уровень начиная с `TALENT_FIRST_LEVEL`. Доступные очки — всегда
  производная (`заработано − вложено`), отдельного счётчика в состоянии нет.
- Правила вложения — в `game/talents.ts`, каждый отказ отдельным кодом
  (`no-points`/`max-rank`/`branch-locked`); текст причины рендерит UI.
- Сброс за золото, цена растёт от `talentResets`. Сброс обнуляет ранги
  и пересчитывает статы.
- НАСТРОЙКА ИГРОКА — НЕ ХАРАКТЕРИСТИКА, и таланту её трогать нельзя. Порог
  привала (`restThreshold`) игрок ставит ползунком и ждёт, что игра ему
  следует; талант, молча сдвигавший его вверх, читался как поломка — на
  экране 60 %, а герой уходил отдыхать на 72 %. Три таких таланта удалены в
  четвёртую ночь, на их местах — таланты на ДЛИНУ привала (`restDuration`,
  процентом: секунды уже заняты соседними талантами той же ветки). Держится
  `content:check` (`SETTING_STAT_IDS` в схеме) с битым образцом.
- УДАЛЁННЫЙ ТАЛАНТ ВОЗВРАЩАЕТ ОЧКИ СВОБОДНЫМИ. Отдельного счётчика доступных
  очков нет — они считаются как «заработано минус вложено», — поэтому
  миграции достаточно убрать ранги (`REMOVED_TALENT_IDS` в `game/save.ts`).
  Молча съесть очки у ветерана нельзя ни при какой правке дерева.
- Таланты ускорения выражаются модификатором `haste` и НИКОГДА плоской
  прибавкой к `weaponSpeed`: иначе один талант увёл бы скорость оружия
  в ноль или в минус, а `swingTime` — в бесконечность. Ускорение живёт
  в долях, поэтому «+10% скорости» — это `{ stat: 'haste', kind: 'flat',
  value: 0.1 }`, а не `percent` (процент от нуля даёт ноль). Источник
  модификатора на итог не влияет — закреплено тестом «талант на +10% haste
  даёт тот же swingTime, что и предмет на +10% haste», а запрет на
  `weaponSpeed` в талантах — отдельным тестом по данным дерева.

## Автокаст

- Настройки автокаста — часть состояния и сейва: галка `autocast` и `priority`
  на каждое умение. ПРИОРИТЕТ — ЭТО ПОРЯДОК СЛОТОВ, своего числа у него нет
  (см. «Умения»). Автокаст жмёт ПЕРВОЕ доступное по этому порядку, у которого
  хватает маны и вышел кулдаун.
- Разница между авто и рукой возникает ЕСТЕСТВЕННО, из ровно двух правил:
  задержка реакции `AUTOCAST_DELAY_MS` после того, как умение стало доступно,
  и то, что автокаст не придерживает кулдауны (добивает моба крупным умением,
  урон уходит в перебой). Множителей «за автоматизацию» нет и быть не должно.
- Потолок отставания `AUTOCAST_MAX_LOSS` — это СНЯТИЕ лишнего штрафа, а не
  добавление нового; точка отсчёта — та же ротация, сыгранная руками.
- ЛЕЧЕНИЕ ВПЕРЕДИ УРОНА: автокаст жмёт лечащее умение ТОЛЬКО когда здоровье
  ниже его порога из данных, и тогда — раньше любого боевого умения,
  каким бы ни был приоритет игрока. «Беречь ману на лечение»
  (`holdManaForHeal`, настройка автокаста, в сейве, по умолчанию включена):
  боевое умение автокаста не жмётся, если после него не останется на одно
  лечение; руками игрок волен потратить всё. Без лечащего умения у класса
  настройка ничего не делает. Модель боя знает о лечении той же формулой
  долгосрочных средних (`healCycle` в `combat.ts`): лечение срабатывает в
  последнем бою цикла, когда тот пересекает порог, спасает цикл от привала
  с вероятностью, и число спасений геометрическое; мана на него идёт
  фиксированным кастом в ротацию первой. ПОРОГ ЛЕЧЕНИЯ СТОИТ НИЖЕ ПОРОГА
  ПРИВАЛА (0.55 против 0.6 по умолчанию), и это решает, сколько привалов оно
  снимает: медианный бой до порога не доходит, глубокий — доходит. Замер
  тиком: порог 0.5 снимал 10–13 % простоя на привалах, 0.55 — 28–33 %
  (цель 20–35 %), порог у привального убрал бы привалы вовсе. Цена
  медианного боя от САМОГО ЛЕЧЕНИЯ не менялась ни разу: когда его заводили,
  урон мобов под него не поднимали, и контракт цены боя остался на прежних
  числах. Урон мобов с тех пор поднимали дважды — под возврат коридора
  13–20 % и под броню, — но ни один из подъёмов лечением не вызван.
- ЖЕЛЕЗНОЕ ПРАВИЛО: `оффлайн <= автокаст <= ручная игра`. Оффлайн считается
  по модели автокаста (та же задержка и приоритеты) и режется на
  `OFFLINE_EFFICIENCY`. По идеальной игре оффлайн не считается никогда.
- `estimateCombatRate(state, mode)`: `'auto'` (по умолчанию) — что герой выдаёт
  сам, `'manual'` — что выйдет, если жать умения самому. UI показывает обе.
- НА ЭКРАНЕ У АВТОКАСТА СВОЁ МЕНЮ, и стоит его кнопка вплотную к ряду
  умений, который он и настраивает: общий выключатель, галка и приоритет на
  каждое умение, резерв ресурса, «беречь ману на лечение». Раньше кнопка
  только включала ротацию, а её настройки лежали в «Талантах» — за кнопкой,
  которая про другое. Подробности — раздел «Экран и меню».

## Привал

- ПОРОГ ПРИВАЛА — ПОЛЗУНОК 0–100 % шагом `REST_THRESHOLD_STEP` (10 %), а не
  четыре пресета. Между 40 % и 60 % разница в цене боя ощутима, а выбрать там
  было нечего; «никогда» стояло в одном ряду с процентами, будто это такой же
  процент. Значение прижимается к шагу ОДНОЙ функцией (`snapRestThreshold`),
  и зовут её и экшен стора, и миграция сейва.
- ПОТОЛОК — ЕДИНИЦА, а не 0.95. Ползунок обещает сто процентов, и обещание
  обязано быть правдой: «отдыхать после любой царапины» — законный (плохой)
  выбор игрока, а игра называет, что нельзя, и не называет, чем кончится.
- ПОДПИСЬ ПОЛЗУНКА ГОВОРИТ ДЕЙСТВУЮЩУЮ ДЛИНУ ПРИВАЛА (`restDurationMs`), а не
  константу из данных: таланты её режут, еда режет вдвое, и число из
  `data/balance.ts` было бы неправдой ровно у того, кто эти таланты вложил.
  На нуле подпись другая: привалов не будет вовсе.

## Зоны

- Зоны — данные (`data/zones.ts`): `monsterLevelRange`, `monsterPool`,
  `rewardMultiplier`, `isSafe`. Ровно одна зона обязана быть `isSafe` — в неё
  возвращает смерть.
- ЗОНУ ОТКРЫВАЕТ ДАНЖ, А НЕ УРОВЕНЬ. Поля `unlockRequirement` у зоны НЕТ:
  требования шли тройками, а полосы мобов пятёрками, и последняя зона
  открывалась на 58 уровне при мобах 96-100. Двадцать зон раскладываются без
  остатка: четыре стартовых плюс восемь данжей по две. Ритм — десять уровней
  зоны, данж, десять уровней. Зона, которую не открывает ни один данж, открыта
  с начала игры (`INITIAL_ZONE_IDS`), и таких ровно четыре.
- Открытые зоны лежат в сейве ОТДЕЛЬНЫМ полем (`unlockedZoneIds`), а не
  выводятся из `dungeonsCleared`: «данж пройден» это достижение (постоянный
  бонус к опыту и уникальные награды), «зона открыта» — доступ. Миграция
  старых сейвов обязана вернуть зоны, не выдав достижений.
- Мобы не лежат в данных готовыми: `data/monsters.ts` хранит архетипы (роль)
  и ФОРМУЛУ масштаба от уровня. Числа hp/урона/наград считает `buildMonster`,
  логика их не выводит.
- `spawnMonster(zone, rng, heroLevel)` — броски строго в том же порядке:
  сперва уровень, потом архетип из пула.
- УРОВЕНЬ МОБА ПРИ СПАВНЕ ЖМЁТСЯ К УРОВНЮ ГЕРОЯ, а не берётся по полосе
  равновероятно: 70% ровно его уровень, по 10% на ±1, по 5% на ±2
  (`SPAWN_LEVEL_SPREAD` в `data/monsters.ts` — проценты в ДАННЫХ, сумма
  проверяется тестом). ПОЛОСА ЗОНЫ СИЛЬНЕЕ РАСПРЕДЕЛЕНИЯ: смещения за её край
  отбрасываются, оставшиеся веса нормируются, и герой выше полосы получает
  мобов, прижатых к верхней границе. Равномерная полоса ломала то, ради чего
  заведена: пришедший в зону дрался с мобом на четыре уровня старше в пятой
  части боёв, доигравший её — с мобом, умирающим с двух ударов.
- МОДЕЛЬ ЗНАЕТ ТО ЖЕ РАСПРЕДЕЛЕНИЕ. `zoneSpawnVariants(zone, heroLevel)` —
  единственный источник «каких мобов этому герою выдают и с какой
  вероятностью»; по нему считают темп зоны, худший бой, `maxMonsterHit` и
  `estimateZoneTtk`. Равномерное усреднение по полосе (`zoneMonsterVariants`)
  осталось ровно для вопроса «что вообще водится в зоне».
- Опасность зоны НЕ пишется текстом в данных: `game/zones.ts` считает прогноз
  (`forecastZone`) через ту же `estimateCombatRate`, что и бой, и отдаёт код
  вердикта. Игроку вердикт НЕ показывается (см. «Экран и меню»): им
  пользуются `offlineZone`, оффлайн-агрегат и тесты.
- Темп зоны (`zoneRate`) — среднее по мобам, которых спавн выдаёт ЭТОМУ герою,
  ВЗВЕШЕННОЕ их вероятностями (пул × веса уровней). Смертность считается один
  раз на зону по средней потере HP: запас HP у героя общий на всю череду боёв.
- Оффлайн идёт шагами по `OFFLINE_CHUNK_MIN`: набранные уровни меняют статы,
  а значит и темп следующего шага.
- ЛУТ В ОФФЛАЙНЕ ПАДАЕТ. Внутри шага по числу убийств крутится ТА ЖЕ
  `rollLoot` и ТА ЖЕ `stashLoot`, что в тике: второй модели дропа и второй
  копии правил сумки нет. Отдельного коэффициента у лута тоже нет — число
  убийств уже урезано на `OFFLINE_EFFICIENCY`. Уровень находки — по среднему
  мобу зоны, как и весь остальной агрегат. Автонадевания по-прежнему нет:
  герой возвращается к сумке находок.
- ШТРАФ ОПЫТА ЗА ОТСТАВАНИЕ считается по уровню КОНКРЕТНОГО МОБА
  (`gap = уровень героя − уровень моба`), а не зоны: зона накрывает пять
  уровней, и по её границе штраф врал бы половине пула. Ступени —
  `XP_GAP_PENALTY` в `data/balance.ts`, границы и коэффициенты живут там и
  двигаются только там.
- Штраф бьёт ТОЛЬКО по опыту. Золото, материалы, травы и лут не трогаются:
  отставшие зоны обязаны оставаться полезными для фарма низких материалов,
  иначе за ними будет некуда пойти. ЦЕНА ЭТОГО ПРАВИЛА ИЗМЕРЕНА: герой
  двадцатого уровня на стартовом лугу зарабатывает 106% того, что заработал
  бы в своей зоне. Предложение частичного штрафа золота лежит в
  `data/balance.ts` рядом со штрафом опыта — не применено, решение открыто.
- РАЗРЫВ В ДРУГУЮ СТОРОНУ — МОБ ВЫШЕ ГЕРОЯ — бьёт по ВХОДЯЩЕМУ УРОНУ:
  `levelGapDamageMult`, пять уровней бесплатно (ширина полосы зоны), дальше
  +30% за уровень. Ставкой роста урона это не заменяется: у линейных функций
  отношение соседних зон от ставки не зависит и с уровнем стремится к
  единице — резкой отсечки линейная кривая не даёт ни при каком числе.
  Контракт: герой уверенно держит зоны до +5 и с риском до +10, глубже никак.
- Штраф знают все, кто считает опыт во времени: начисление за убийство,
  `zoneRate` (а через неё прогноз зоны и оффлайн). Кривую стоимости уровня
  он НЕ трогает — она считается по зоне, куда игра ведёт героя, где разрыва
  нет по определению.
- Прогноз зоны отдаёт долю опыта полем `xpShare` (1 / 0.5 / 0) по среднему
  уровню мобов — тем же разрывом, что и `levelGap` рядом. Точное начисление
  идёт по каждому мобу, поэтому зона на границе ступени платит между двумя
  долями; настоящее число видно в `xpPerHour`. Текст рендерит UI.

## Цена боя

Рядом с контрактом темпа (TTK 8-15 секунд, `PACING` в `data/balance.ts`)
стоит второй, о цене той же схватки:

```
Герой уровня L в актуальном для L снаряжении теряет 13–20 %
максимального здоровья за один бой с МЕДИАННЫМ мобом своей зоны.
ВАЛОВО — до лечения умением, с учётом регенерации. Действует с первого
уровня, без скидок на первые уровни. Числа коридора — FIGHT_COST_TARGET
в data/balance.ts.
```

ЧИСЛО ВТОРОЕ, РЯДОМ: `FIGHT_COST_NET_TARGET` (9–14 %) — сколько остаётся на
полоске ПОСЛЕ того, как герой заплатил маной за лечение. Коридор нетто
МЯГКИЙ и живёт предупреждением, а не падением: он зависит от того, сколько
маны у класса и как настроен автокаст, то есть от решений игрока, а не от
данных мобов. Контракт стоит на ВАЛОВОЙ цене; нетто ходит рядом, чтобы
разрыв «есть мана / нет маны» был виден в отчёте.

Замер по Стражу на всех двадцати зонах: **валово 14.1–19.2 %, в среднем
16.5 %; нетто в среднем 10.0 %.** Обе величины внутри своих коридоров.

ДВИГАЕТСЯ КОРИДОР ОДНИМ ЧИСЛОМ — `MONSTER_BASE.damage`; всё остальное
(скидка ранних полос, множители боссов, пороги тестов) считается от него.

ИСТОРИЯ ЧИСЛА, ЧТОБЫ ЕГО НЕ КРУТИЛИ ПО КРУГУ. Коридор был 20–25 %; по живой
игре это оказалось жестковато, и владелец снял врагам пятнадцать процентов
урона. Вторая ночь опустила запись до 9–15 % — но это была ПЕРЕКАЛИБРОВКА
ИНСТРУМЕНТА, а не игры: прежняя модель боя не знала, что привал наливает
ману до полного, и считала бой на 15 % длиннее настоящего. Третья ночь
вернула 13–20 % и вернула их ПОДЪЁМОМ УРОНА МОБОВ — то есть решением о том,
какой игра должна быть, а не о том, какая она есть. Здоровье мобов при этом
не трогалось ни разу: длину боя держит оно, цену — урон.

ПОСЛЕДНИЙ ПОДЪЁМ УРОНА — ЭТО БРОНЯ, А НЕ ПРАВКА КОРИДОРА.
`MONSTER_BASE.damage` поднят 18.36 → 38.87 ровно потому, что броня срезала
около половины входящего (см. «Броня»), а коридор обязан остаться на месте.
Полоса 1–5 выведена из подорожания отдельным множителем `EARLY_HP_DISCOUNT`:
у героя первых уровней брони ещё нет, и общий множитель ударил бы по нему
дважды.

- ДВА КОНТРАКТА НА ОДНУ СХВАТКУ, и ручки у них разные: длину боя задаёт
  здоровье моба, цену — его урон. Правишь одно — второе не трогается.
- КОНТРАКТ СТОИТ НА ЭТАЛОННОМ ГЕРОЕ (`referenceBuild`, модель `equipUpgrades`),
  а не на формуле «урон моба = 22% запаса героя». Это разные вещи, и вторая
  убивает смысл живучести и брони: сколько их ни набирай, моб снимал бы ту же
  долю. Числа расходятся САМИ — снаряжение лучше эталона теряет меньше 20%,
  хуже эталона больше 25%, — и тест обязан проверять ОБА отклонения.
  Односторонний тест не отличает верную реализацию от этой подмены.
- МЕРИТСЯ НА ВХОДЕ В ЗОНУ, то есть на уровне, с которого игра в неё приводит.
  Внутри зоны доля падает сама: герой растёт пять уровней, а мобы стоят на
  месте. Это не дырка в контракте, а награда за то, что зону доигрывают.
- ДОПУСК ±2 ПУНКТА, и он не от лени. Цена боя — это `урон моба × число ударов
  за бой ÷ запас героя`, а число ударов целое: один лишний удар из шести-восьми
  двигает долю на два-три пункта. Сверху ложится ширина коридора темпа: бой
  на 15 секундах стоит на четверть дороже боя на 12, а оба законны. Свежий
  замер: в 13-20% укладываются все двадцать зон Стража (14.1-19.2%). Сузить
  коридор цены можно только сузив коридор темпа, и это отдельное решение.
- ЦЕНА ХУДШЕГО БОЯ — ДРУГОЕ ЧИСЛО, и именно оно решает, гибнет герой или нет:
  здоровяк с верхнего края полосы стоит 18.0-25.8% запаса ПО ВСЕМ ДВАДЦАТИ
  ЗОНАМ. Порог привала по умолчанию стоит ВЫШЕ него (см.
  `REST_HP_THRESHOLD_DEFAULT`).
- ЛЕСТНИЦА ХУДШЕГО БОЯ ВЫРОВНЯЛАСЬ СПАВНОМ ВОКРУГ УРОВНЯ ГЕРОЯ. Было 15-42%
  с провалом в стартовой зоне (38%): новичок в одном белом клинке встречал на
  лугу мобов впятеро старше себя, и первая зона была самой дорогой схваткой
  всей игры. Теперь ему выдают +2 уровня максимум, коридор сузился вчетверо, и
  стартовая зона (24.1%) стоит в одном ряду с последней. Контракт держит это
  двумя тестами: коридор 15-30% на каждой зоне и разрыв «первая против
  последней» меньше 12 пунктов — односторонний коридор пропустил бы возврат
  провала на краю лестницы.
- ЦЕНА БОЯ ЗАДАЁТ АПТАЙМ. При 13-20% за бой герой уходит на привал после
  второго-третьего убийства: модель зоны даёт 19-31% времени вне боя, полный
  путь 1..100 — 33% и 36% по классам (было 0.3-1.0%). Этот простой обязан
  быть в оффлайн-агрегате: он там и есть, через `uptime` из `farmCycle`, и без
  него оффлайн завысил бы добычу на треть. Простой от привала и простой от
  смерти — РАЗНЫЕ вещи, их различает поле `dies` у `zoneRate`; вердикт зоны
  смотрит на него, иначе любая зона читалась бы как смертельная.
- УБИЙСТВО ВИДНО СНАРУЖИ ПО ДВУМ ПРИЗНАКАМ, а не по одному: взведённый таймер
  респауна ИЛИ уход на привал. Решение об отдыхе принимается после убийства и
  до `applyRespawn`, и уход обнуляет таймер — считая только по нему, прогон
  недосчитывался почти сорока процентов убийств.

## Дизайн-система

- `ui/tokens.css` — ЕДИНСТВЕННЫЙ источник визуальных величин: палитра,
  шкала отступов (4/8/12/16/24/32), радиусы, тени, типографика, длительности,
  брейкпоинт. В компонентах не должно быть ни одного hex-литерала и ни одного
  отступа числом — только `var(--…)`. Держится тестом `ui/kit/kit.test.ts`.
- Тема ОДНА и тёмная. Переключалки светлой/тёмной нет и не будет: игра, в
  которую смотрят часами, отладочные оверлеи всегда были тёмными, а цвета
  редкостей на светлом фоне выцветают.
- Цветов редкостей в токенах НЕТ намеренно — они живут в `data/rarity.ts`
  вместе с весами рулетки. Компонент получает цвет через `--rarity-color`,
  который проставляет `ui/kit/rarity.ts`. Второго набора быть не должно —
  это тоже проверено тестом.
- Семантика цвета: `--c-damage` урон, `--c-heal` здоровье, `--c-mana` мана,
  `--c-xp` опыт и прокачка, `--c-gold` золото, `--c-warning` предупреждение.
  `--c-accent` — про ВЗАИМОДЕЙСТВИЕ (кнопка, фокус, наведение) и намеренно не
  совпадает ни с одной семантикой: «нажми меня» не должно путаться с «тут урон».
- Примитивы `ui/kit/`: `Panel`, `Button`, `StatBar`, `IconSlot`, `Tooltip`,
  `NumberText`, `Tag`. Они НЕ знают про игровое состояние — только пропсы.
  Компонент, который лезет в стор из примитива, сломал правило.
- Шрифт один — Inter, лежит в `public/fonts/` подмножествами кириллицы и
  латиницы. Из сети не тянется: страница выглядит одинаково везде и
  открывается без интернета. Табличные цифры включены глобально.
- Витрина `/ui` (только при `?debug=1`) показывает все примитивы во всех
  состояниях, всю палитру, все редкости и всю шкалу типографики на одной
  странице. Добавил примитив или состояние — добавь его туда же.

## Лестница открытий и лестница покупок

- ЗАКРЫТО ЗНАЧИТ НЕ ВИДНО. Панель механики, до уровня которой игрок не дошёл,
  НЕ ОТОБРАЖАЕТСЯ ВОВСЕ — ни серой, ни с замком, ни строкой «откроется на N
  уровне». Обратный отсчёт до контента отвечает на вопрос, который лестница
  открытий держит закрытым. Так спрятаны таланты (до `TALENT_FIRST_LEVEL`),
  ремёсла (`CRAFT_UNLOCK_LEVEL`), зачарование (`ENCHANT_UNLOCK_LEVEL`), храм,
  задания. Коды отказа при этом ОСТАЮТСЯ в логике: они нужны тестам и
  оффлайну, просто ни один экран их больше не рисует.
- МЕХАНИКА ОТКРЫВАЕТСЯ ЦЕЛИКОМ, а не по частям. Травничество — один порог на
  сбор, рецепты и склянки: «собирать можно, варить нельзя» было худшим из
  состояний. Порог профессии — ПОЛ для всех её рецептов
  (`PROFESSION_UNLOCK_LEVEL` в `data/recipes.ts`), свой `unlockLevel` рецепта
  его только поднимает.
- ЗАПЕРТАЯ МЕХАНИКА НЕ СОБИРАЕТ РЕСУРС РАНЬШЕ СВОЕГО УРОВНЯ. Правило общее и
  держится `content:check`: источник ресурса не может лежать в зоне ниже
  уровня открытия. Отсюда травы растут только с полосы 41-45 и ни строкой
  раньше. Битый образец — трава в стартовой зоне — лежит в наборе поломок.
- ЛЕСТНИЦА ПОКУПОК (`data/upgrades.ts`) — семь ступеней за золото: пять про
  место в сумке, две открывают положения переключателя «что делать с лишним»
  (не трогать / продавать / распылять). НИ ЕДИНИЦЫ СИЛЫ за золото не
  продаётся: иначе оно стало бы второй лестницей прокачки рядом с уровнями и
  предметами, и бюджет силы пришлось бы делить ещё и с ним. Держится тестом.
- ЦЕНА ПОКУПКИ — В ЧАСАХ ДОХОДА своего уровня (`goldPerHourAt`), как и пошлина
  крафта. Числом её пришлось бы держать в двух местах — в цене и в кривой
  золота, — и они разъехались бы на первой правке.
- ЦЕНА ОКРУГЛЯЕТСЯ ДО ДВУХ ЗНАЧАЩИХ ЦИФР (`GOLD_PRICE_SIGNIFICANT_DIGITS` в
  `data/upgrades.ts`, `roundPrice` в `game/upgrades.ts`). Она СЧИТАЕТСЯ из
  кривой дохода, а не назначается, и без округления выходит «4713» —
  число, которое читается как случайное, потому что оно и есть случайное.
  Округление на ПОКАЗЕ было бы враньём: списывалось бы другое.
- ЦЕНА ВИДНА ВСЕГДА, а не только когда хватает: она на кнопке, и рядом
  строка «не хватает N», если не хватает. Скрытая цена превращает цель в
  стену без расстояния до неё — то же правило, что у сброса талантов.
- РАЗМЕР СУМКИ И ОТКРЫТЫЕ ПОЛОЖЕНИЯ РАЗБОРА — ПРОИЗВОДНЫЕ от списка покупок
  (`game/upgrades.ts`), а не поля состояния: отдельные поля пришлось бы чинить
  миграцией при каждой правке лестницы. `INVENTORY_SIZE` остаётся БАЗОЙ.
- ЖЕЛЕЗНОЕ ПРАВИЛО СУМКИ ДЕЙСТВУЕТ И ЗДЕСЬ: разбор на лету убирает мусор, а
  не находки. Вещь, лучшая хоть по одной оси, не продаётся и не распыляется
  ни при каком положении переключателя.

## Крафт

- ПОШЛИНА КРАФТА — ДОЛЯ ЧАСОВОГО ДОХОДА, а не число (`CRAFT_TOLL_HOURS` в
  `data/recipes.ts`): еда 0.125 часа, склянка 0.375, кованая вещь 1, уникум 2.
  Числом её пришлось бы держать в двух местах — в цене и в кривой золота, — и
  они разъехались бы на первой правке баланса. Зачарования пошлины не платят:
  они стоят пыль.
- Часовой доход берётся ТАМ ЖЕ, где кривая опыта берёт цену уровня: типичный
  моб своей зоны на убийства в час (`goldPerHourAt`). Второй модели дохода в
  игре нет, и совпадение модели с прогоном проверяется тестом.
- Уровень рецепта — «самый глубокий из самых мелких»: каждый вход стоит
  столько, сколько стоит мельчайшая зона, где он есть, а рецепт — столько,
  сколько стоит самый труднодоступный из входов. Иначе за луговой травой
  пришлось бы ходить на девяностый уровень.
- Цена видна ДО нажатия, кнопка заперта отказом с кодом (`gold`), текст рисует
  UI. Порядок отказов: уровень, запертость, материалы, золото, место в сумке.

## Кран золота

- КРАН ЗОЛОТА СОСТОИТ ИЗ ДВУХ ДОЛЕЙ, и они лежат в данных одним числом:
  `GOLD_SOURCE_SHARE` в `data/balance.ts` — 30% платит убитый моб напрямую,
  70% приносит продажа того, что с него упало. Доли делят ОДНО И ТО ЖЕ
  `MONSTER_BASE.goldReward`, поэтому общий кран от их правки не двигается;
  сумма обязана быть единицей и проверяется `content:check`.
- ЦЕНА НАХОДКИ РАСТЁТ ОТ ЕЁ УРОВНЯ И ТИРА (`itemSellPrice` в `data/loot.ts`),
  и кривая берётся ТА ЖЕ, что у наград моба: `rewardScale` плюс множитель
  зоны. Своей кривой у цены быть не должно — она разъехалась бы с доходом.
  База (`ITEM_SELL_BASE`) не выбрана, а ПОСЧИТАНА: доля крана, делённая на
  `DROP_CHANCE` и на средний множитель тира (`EXPECTED_SELL_MULT`).
- МОДЕЛЬ ДОХОДА ЗНАЕТ ОБА СЛАГАЕМЫХ и берёт их с ОДНОГО И ТОГО ЖЕ моба:
  находка падает с него и несёт его уровень, а не уровень героя.
- ДОХОД ЗА ЧАС — КОШЕЛЁК ПЛЮС ПОДОРОЖАНИЕ СУМКИ (`incomePerHour` у прогона).
  Непроданная находка — отложенное золото, а не потерянное: сумка это буфер
  на дюжину мест, и в установившемся режиме каждая новая вытесняет одну
  старую в продажу. Мерить один кошелёк значило бы мерить скорость
  наполнения буфера — замер по нему давал 43-81% расхождения с моделью.
- ОКНО ЗАМЕРА ДОХОДА — ЧЕТЫРЕ ЧАСА, А НЕ ОДИН. Награда моба
  детерминирована, а цена находки разыгрывается тяжелохвостой рулеткой:
  разброс ОДНОЙ находки — 143% от среднего, и за час отношение соседних
  ступеней кривой гуляло вдвое.
- ПРОДАТЬ ИЛИ РАСПЫЛИТЬ — НАСТОЯЩИЙ ВЫБОР, и разрыв между путями держится
  тестом: меньше трёх раз и НЕ РАСТЁТ с уровнем. Замер — ×2.62 на всей
  лестнице. Пока цена не знала об уровне, разрыв был ×60 на десятом уровне и
  ×1597 на сотом: распылять было выгоднее в полторы тысячи раз.

## Бюджет силы

- ВСЁ, ЧТО ДАЁТ СИЛУ, СТОИТ В ОДНОЙ ЛЕСТНИЦЕ. База — эталонное снаряжение
  своего тира (не голый герой: на сотом уровне он не выживает, и множитель
  от него бесконечен при любых числах). Поверх неё множителями идут таланты,
  зачарования и зелья, отдельными строками — реликвия с проком, каденция
  апгрейдов и лечение. Коридоры лежат в `POWER_BUDGET` (`data/balance.ts`),
  прибор — `game/__tests__/power-budget.test.ts` (дорогой набор).
- **НОВАЯ СИСТЕМА, ДОБАВЛЯЮЩАЯ СИЛУ, ОБЯЗАНА ПОЛУЧИТЬ СТРОКУ В БЮДЖЕТЕ. Не
  помещается — уменьшается она или чужая строка.** Без этого правила сумма
  растёт молча: каждая система по отдельности «даёт немного», а вместе они
  ломают и темп, и цену боя.
- ПОЛ КОРИДОРА ВСЕГДА ВЫШЕ ЕДИНИЦЫ. Снятый источник обязан выпадать из
  коридора — иначе это не контракт, а украшение.
- БРОНЯ ПОЛУЧИЛА СВОЮ СТРОКУ (`POWER_BUDGET.multipliers.armor`) в тот же
  день, когда появилась, — правило выше применено к самому себе. Заодно
  пришлось опустить ПОЛ строки талантов: броня подняла аптайм героя БЕЗ
  талантов сильнее, чем с ними, и отношение «с талантами / без» просело.
  Это не ослабление талантов, а смена базы, и причина записана рядом с
  числом.
- ДОЛИ УРОНА — тоже строки бюджета: автоатака, умения, проки, и они дают в
  сумме сто процентов по построению. Страж — класс УМЕНИЙ (две трети урона
  через ротацию), и это решение, а не дефект.
- СТРОКА В РЕЖИМЕ ОТЧЁТА — законный исход, но только с записанной причиной.
  Коридор автоатаки сейчас такой: замер 28.7 % при поле 30 %, а ручки,
  которой это чинится, нет — поднять автоатаку можно лишь уроном оружия, а он
  держит контракт темпа. Предупреждение печатается, прогон не роняется,
  расхождение висит открытым вопросом.

## Прогон баланса

- `game/simulate.ts` — headless-симуляция: `simulate({ hours, zoneId, build })`
  крутит НАСТОЯЩИЙ конвейер тика N игровых часов и возвращает метрики
  (убийств/золота/опыта/смертей в час, время до следующего уровня, итоговый
  уровень). Своей модели боя у прогона нет — иначе он мерил бы не ту игру.
- Метрики считаются ТОЛЬКО по наблюдаемому снаружи состоянию: убийство — по
  взведённому таймеру респауна, смерть — по переходу `alive → dead`, каст —
  по подскочившему кулдауну, урон — по шине `AttackEvent`. Ради прогона в тик
  не добавлено ни одного счётчика.
- Билд задаётся источниками статов, как в игре: уровень, уровень вещей,
  надетое оружие, ранги талантов, галки автокаста. Автонадевание в прогоне выключено —
  иначе билд подменится на середине.
- `freezeLevel` держит героя на стартовом уровне: за час свободного прогона
  герой уходит на десятки уровней вперёд, и строка «уровень 1» на самом деле
  мерит уровни 1..30. Сравнивать зоны между собой можно только замороженными.
- Зона задаётся напрямую, без проверки открытости: это измерительный прибор,
  и «что будет, если сунуться раньше времени» — законный вопрос. Правило входа
  живёт в `travelToZone` и продолжает работать в игре. Герою прогона зоны
  проставляются моделью `unlockedByLevel`: он делает данж, когда тот
  открывается, — иначе прибор мерил бы героя, запертого в стартовой четвёрке.
- Эталонный герой одевается НЕ С ПЕРВОЙ СЕКУНДЫ: первую зону он проходит в
  стартовом комплекте (одно белое оружие) и переодевается на первом переезде.
  Полный средний комплект на первом уровне описывал бы героя, которого не
  существует, — против мобов стартовой зоны он быстрее настоящего вдвое.
- НАБОР `game/__tests__/balance-*.test.ts` печатает таблицы и держит свойства
  баланса: прогресс монотонный по зонам, доминирующей зоны нет, десятый
  уровень с нуля берётся за 15–28 минут игрового времени, подходящая по
  уровню зона не убивает, три оружия с равным уроном оружия в секунду
  сходятся в пределах допуска. Файл был ОДИН и назывался `balance.test.ts`;
  он держал 87 % всей работы матрицы, а раннер раскладывает по ядрам ФАЙЛЫ,
  а не тесты, — поэтому его разрезали (см. `docs/PERF-REPORT.md`). Новый
  контракт баланса кладётся в подходящий файл семейства, а не сваливается
  обратно в один.
- Инвариант «равный урон оружия в секунду — равный итог» держится там, где бой
  длится больше десятка замахов. Когда моб умирает с одного удара, лишний урон
  крупного замаха пропадает, и быстрое оружие выигрывает числом замахов —
  это перебой, а не поломанная нормализация. Отдельная таблица в тесте
  показывает, где проходит граница.
- Страница `/balance` (только при `?debug=1`) считает те же таблицы на лету.
  Числа пресета — `BALANCE_PRESET` в `simulate.ts`, общий для теста и страницы.
  Игровой цикл на этой странице не запускается: прибор не фармит за игрока.

## Экран и меню

- «Игра называет, ЧТО сделать нельзя, и никогда — ЧЕМ КОНЧИТСЯ попытка.
  Ограничение словами, исход молчит. Игрок имеет право ошибиться.»
  Поэтому вердикт зоны (`forecastZone`: по силам / риск / смерть / не по
  зубам) в интерфейсе НЕ показывается — ни словом, ни цветом, ни иконкой;
  сама функция остаётся, ей пользуются `offlineZone`, оффлайн-агрегат и
  тесты. Прогноза схватки с боссом до входа в данж нет и не будет:
  ограничения по уровню, зоне, смерти и «уже внутри» — это «нельзя», а не
  «умрёшь». Факты показываются: полоса уровней мобов, доля опыта (правило
  штрафа за отставание, а не прогноз), золото и опыт в час числом. Прогноз
  худшего боя рядом с ползунком привала остаётся: это настройка
  собственного правила игрока, а не ворота в контент.
- Боевая сцена — главный элемент экрана и видна ВСЕГДА, при любом открытом
  меню. ПОСТОЯННАЯ ЗОНА — ОДНА СЕТКА НА ТРИ ПОЛОСЫ (`.permanent`, grid
  `auto 1fr auto`):
  1. столбец кнопок «где меняешь» · сцена · столбец кнопок «где читаешь»;
  2. «Умения» · ряд из четырёх слотов действий с порогом привала справа;
  3. строка уровня с полосками во всю ширину.
  Заголовка игры в ней нет: «Idle RPG» стояло над сценой на каждом экране и
  стоило ей вертикали — самого дорогого, что есть на телефоне; название
  осталось в заголовке вкладки. Трёх колонок (герой / сцена / умения) больше
  нет: делить ширину со сценой значило показывать бой в трети окна. Состав
  зоны — шесть ячеек, и каждая названа в `tests/layout.spec.ts`.
- КНОПКИ МЕНЮ СТОЯТ ПО БОКАМ СЦЕНЫ, а не под всей зоной. Сцена — главный
  элемент экрана, и кнопки вокруг неё читаются как рамка вокруг главного;
  те же кнопки, отодвинутые под полоски героя, читались как ещё один ряд
  среди прочих. На мобильном столбцов нет — кнопки уезжают в полосу у низа
  окна.
- СЕТКА ОДНА НА ВСЮ ЗОНУ, и это ради выравнивания: боковые колонки шириной
  `auto` подстраиваются под самую широкую подпись, и «Умения» встают под
  левым столбцом сам, без подбора чисел. Двумя независимыми рядами ширины
  разъехались бы на первой же кнопке с длинным словом. Ячейки расставлены
  ЯВНО (`grid-column`/`grid-row`), а не автопотоком: на узком экране столбцы
  уходят в `position: fixed`, то есть выпадают из потока, и автопоток тут же
  перекладывал бы сцену в первую колонку.
- Пропорции сцены держит РАМА (`ui/BattleScene`), а не картинка: 4:3 на
  мобильном, 16:9 от 720px. Содержимое сцены растянуто по раме абсолютно и
  сдвинуть раскладку не может.
- ОТКРЫТОЕ МЕНЮ СЖИМАЕТ СЦЕНУ НА МЕСТЕ и ложится ПОД постоянной зоной во всю
  ширину. Прятать сцену нельзя: «сцена видна всегда» — правило, и меню его
  не отменяет. Уводить её в угол — тоже: кнопки стоят по её бокам, и сцена,
  ушедшая из потока, оставила бы между столбцами дыру в полтысячи пикселей,
  а сами столбцы разъехались бы по краям пустой полосы. Пропорции те же
  16:9, ширина — доля окна между `SCENE_MINI_MIN_PX` и `SCENE_MINI_MAX_PX`
  (`data/render.ts`, числа в ДАННЫХ, а не в CSS).
- В СЖАТОЙ СЦЕНЕ НАБОР ЭФФЕКТОВ СОКРАЩЁН: вспышка попадания, полоски здоровья и
  РОВНО ОДНО всплывающее число (`SCENE_MINI_FLOATERS`). Ни тряски, ни
  сдвигов, ни выпадов — и держится это ОБНУЛЁННЫМИ РУЧКАМИ ДВИЖЕНИЯ
  (`--lean`/`--lunge`/`--kick` в `.host.mini`), а не выключением каждого
  эффекта поимённо: все три считаются от этих величин. Кольцо лечения и
  вспышка нового уровня в сжатой сцене не рисуются.
- НА УЗКОМ ЭКРАНЕ И СЖИМАТЬ НЕЧЕГО — есть СТРОКА-СВОДКА. Треть от 390px это
  130 пикселей: силуэты сливаются, табличка с именем не помещается, а меню
  всё равно не остаётся места. Под открытым меню сцена схлопывается в одну
  строку — имя, уровень и здоровье моба, — и берётся она ИЗ ВИДА ТЕКСТОВОГО
  РЕЖИМА (`BattlePanel compact`), а не пишется второй раз. Заголовок места и
  полоса замаха уходят вместе со сценой: «одна строка» значит одна строка.
- Ширину окна для этого берёт ПОДПИСКА (`bind:innerWidth`), а не медиазапрос:
  медиазапрос умеет спрятать элемент, но не умеет подменить компонент, а
  сводка — другой компонент, а не сцена в другом размере.

### Восемь меню и что в них лежит

- МЕНЮ ВОСЕМЬ, И ПАТТЕРН У НИХ ОДИН (`MENU_IDS` в `stores/ui.ts`): Герой,
  Сумка, Мир, Таланты, Крафт, Журнал, Настройки, Умения. Было два разных
  паттерна на одну задачу — четыре раздела вкладками внизу и две выдвижки
  поверх низа экрана; два способа показать панель означали два способа её
  закрыть и вечный вопрос, куда класть следующее. Число закреплено
  `stores/ui.test.ts`.
- КНОПКА ОБЯЗАНА СОДЕРЖАТЬ ТО, ЧТО ОБЕЩАЕТ ИМЕНЕМ. Это правило, а не
  разовая уборка: панель, положенная «пока сюда», превращает название
  кнопки в неправду, и игрок перестаёт верить всем остальным.

  | кнопка | что внутри |
  | --- | --- |
  | Герой | карточка статов, кукла и сумка рядом с ней |
  | Сумка | только сумка: находки, продажа, распыление, лестница покупок |
  | Мир | карта зон, храм испытаний, лестница открытий |
  | Таланты | три ветки дерева и цепочка преквестов |
  | Крафт | рецепты и зачарование |
  | Журнал | лог боя |
  | Настройки | текстовый режим, громкости, сейв |
  | Умения | книга умений (выбор четвёрки из одиннадцати) и настройки ротации: общий выключатель, галка и резерв на каждое умение |

- «УМЕНИЯ» — МЕНЮ, А НЕ ПЕРЕКЛЮЧАТЕЛЬ, и это разбор старой ошибки. Кнопка
  называлась «Автокаст», включала и выключала ротацию целиком, а НАСТРОЙКИ
  этой самой ротации лежали в «Талантах» — за кнопкой, которая про другое.
  Теперь за ней ДВЕ панели: книга умений (выбор четвёрки) и настройки
  автокаста этой четвёрки, а общий выключатель — первая строка внутри.
  Порядок именно такой: сперва решают, ЧЕМ играть, и только потом, что из
  этого игра жмёт сама. Место кнопки записано ДАННЫМИ —
  `MENU_SIDE.autocast === 'row'`, — и `menusOn` такую сторону в столбцы не
  выдаёт: ни одной проверки по id ради одного исключения. Подпись берётся из
  `MENU_LOOK`, а не пишется в самой кнопке вторым экземпляром.
- КНИГА УМЕНИЙ ПОКАЗЫВАЕТ ВСЕ УМЕНИЯ КЛАССА, и закрытые тоже — с уровнем
  открытия. Это ОСОЗНАННОЕ исключение из «закрыто значит не видно»: список
  умений — обещание, ради которого играют дальше, и то же исключение уже
  действует у запертой кнопки в ряду. Роль каждого умения написана СЛОВАМИ
  (`ABILITY_ROLE` в `ui/abilityText.ts`): «1.8 урона оружия» не отвечает на
  вопрос, зачем умение нужно, а выбор идёт именно по нему.
- СОСТАВ МЕНЯЕТСЯ В ЛЮБОЙ МОМЕНТ. Никакого «только вне боя»: герой почти
  всегда в бою, и такой запрет был бы запретом навсегда.
- СОСТОЯНИЕ РОТАЦИИ КНОПКА ПОКАЗЫВАЕТ, НО НЕ ЗАВОДИТ: «включён» — когда
  автокаст стоит хотя бы у одного умения. Полувключённого вида у кнопки нет,
  а полувключённая ротация есть, и честнее показать её включённой, чем врать
  выключенной.
- СЛЕВА — ГДЕ МЕНЯЕШЬ, СПРАВА — ГДЕ ЧИТАЕШЬ. Слева Герой, Сумка, Мир,
  Таланты, Крафт; справа Журнал и Настройки — они героя не меняют; «Умения»
  ни в одном столбце, у него сторона `'row'`. Сторона лежит ДАННЫМИ
  (`MENU_SIDE`), а не расстановкой в разметке: иначе следующая кнопка встанет
  наугад.
- ЗАКРЫТОЕ НЕ ВИДНО ВОВСЕ — И ЭТО ПРО САМИ КНОПКИ, а не только про панели за
  ними. Правило лестницы открытий было записано про панели и не применено к
  кнопкам: игрок первого уровня видел «Таланты» и «Крафт» и открывал пустоту.
  Порог — `MENU_UNLOCK_LEVEL` в `stores/ui.ts`, и своих чисел там нет, только
  ссылки на `TALENT_FIRST_LEVEL` и `CRAFT_UNLOCK_LEVEL`: разъехаться с
  порогом самой механики он не может. Меню, которого в карте нет, видно с
  первого уровня.
- ОДНО МЕНЮ ЗА РАЗ. Открытие второго закрывает первое, Esc закрывает
  открытое, повторное нажатие той же кнопки закрывает. Открытое меню НЕ
  сохраняется ни в сейве, ни в настройках машины — это «где я сейчас», а не
  настройка: после перезагрузки игрок хочет видеть бой.
- Esc СНИМАЕТ БЛИЖАЙШЕЕ: сперва вещь из руки, и только если руки пусты —
  меню (см. «Экипировка»). Слушатель клавиши один на игру и висит в
  `App.svelte`: плодить по подписке на каждое из восьми меню значило бы
  восемь слушателей вместо одного.
- Столбцы кнопок ЛИПНУТ К ВЕРХУ окна на десктопе: меню бывают на десять
  экранов, и кнопка «закрыть это и открыть то» не должна уезжать за край.
- ИСКЛЮЧЕНИЕ, И ОНО ОСОЗНАННОЕ: «Герой» открывает куклу И СУМКУ рядом —
  иначе перетаскивать предмет из сумки на слот некуда, два меню разом не
  открываются. «Сумка» при этом открывает ТОЛЬКО сумку: продать и распылить
  можно, не разворачивая куклу. Унифицировать это не надо.
- «РЯДОМ» ЗНАЧИТ РЯДОМ: на широком экране кукла и сумка стоят двумя
  колонками (`.dressing` в `App.svelte`), кукла узкой слева. Друг под другом
  они не помещались ни на одном экране — игрок выбирал находку, прокручивал
  вверх и целился в слот по памяти. На узком экране колонок нет: две по
  190 пикселей это не сетка, а два столбика.
- КАРТОЧКА ГЕРОЯ — ДВА ЧИСЛА КРУПНО, ОСТАЛЬНОЕ ПОД «ДЕТАЛЯМИ». Именно два, и
  именно те же две оси, которыми игра меряет находку (см. «Две оси»): урон в
  секунду и живучесть. Одним числом «лучше» уже мерили — и двуручное било
  связку со щитом ровно потому, что живучесть в это число не входила.
  Развёрнуты детали или нет — «где я сейчас», живёт в `stores/ui.ts`, а не
  в сейве.
- Кнопки умений живут в `ActionBar` под сценой и СМОНТИРОВАНЫ ПРИ ЛЮБОМ
  ОТКРЫТОМ МЕНЮ. Там же единственный на игру `svelte:window onkeydown`:
  спрячешь бар под меню — хоткеи 1/2/3 умрут глобально. Держится тестом по
  случаю НА КАЖДОЕ из восьми меню, а не «на одном и ладно».
- ТЕКСТОВЫЙ РЕЖИМ — полноценный режим, а не заглушка: в нём на месте сцены
  боевая панель, и игра проходится целиком без картинки. Включается ТОЛЬКО
  настройкой (`'on'`); автоопределения нет и не нужно — двумерной сцене
  нечем не завестись, ей хватает обычных элементов страницы. В текстовом
  режиме сцена РАЗМОНТИРОВАНА, а не спрятана (закреплено `budgets.spec.ts`).
  `?scene=off` сильнее любой настройки.
- Настройки интерфейса (текстовый режим, громкость) лежат в СВОЁМ ключе
  localStorage, а не в сейве: это свойства машины, а не прогресс. Открытое
  меню, несомая вещь и развёрнутость «Деталей» не лежат нигде — это «где я
  сейчас». Экспорт сейва не должен увозить на другой компьютер текстовый
  режим чужого экрана.
- ЛИМИТА КАДРОВ НЕТ, и возвращать его не надо. Он появился ради видеокарты
  под трёхмерной сценой; после её удаления настройка резала только игровой
  цикл — то есть частоту, с которой страница просыпается, — а сцена из
  обычных элементов своих кадров не считает. Единственная опция
  производительности — текстовый режим.
- Мобильный: область нажатия не меньше 44px, по горизонтали не вылезает
  ничего ни на одной ширине.

## Боевая сцена (2D)

- Бой рисует ДВУМЕРНАЯ сцена `src/lib/render2d/`: обычные элементы,
  CSS-трансформы и классы состояний. Движка нет: ни three, ни WebGL, ни
  канвы. Сцена заводится везде, где открывается страница, и падать ей нечем —
  поэтому нет ни `reportSceneFailure`, ни автоопределения текстового режима.
  Слои сверху вниз по стеку: фон полосы уровней → спрайт моба → спрайт
  героя → слой эффектов → всплывающие числа. Рама вокруг (`ui/BattleScene`)
  держит пропорции и подпись с именем и здоровьем моба и про рендер не знает.
- ЖЕЛЕЗНОЕ ПРАВИЛО: сцена ТОЛЬКО ЧИТАЕТ игровое состояние и никогда в него
  не пишет. Из `stores/game` ей позволена ровно подписка `gameState`, ни
  одного экшена; всё, что она берёт, собрано одной чистой функцией
  `render2d/model.ts`. Закреплено тестом по исходникам папки. Таймеров
  компонента (`setTimeout`/`setInterval`) в сцене нет — тоже тест.
- ВЕСЬ БЮДЖЕТ ДВИЖЕНИЯ — НА УДАР, НЕ НА ПОКОЙ. Замах виден по отведённой
  руке бьющего, попадание — вспышка на цели, короткий сдвиг и число, крит —
  то же крупнее и цветом предупреждения, умение отличается от автоатаки
  цветом следа и числа, лечение — кольцо у ног героя и зелёное число,
  смерть моба — короткое затухание, привал — своя фаза сцены с подписью,
  а не пустая площадка. Длительности — константы в `data/render.ts`.
- Эффекты — это КЛАССЫ СОСТОЯНИЙ С МЕТКОЙ ВРЕМЕНИ, снимаемые в кадре
  игрового цикла, а не CSS-анимации: под `prefers-reduced-motion` глобальный
  стиль режет длительности до миллисекунды, и ключевой кадр не был бы виден
  вовсе. Сама настройка уважается: тряска и сдвиги под ней обнуляются,
  вспышки и числа остаются.
- Всплывающие числа идут от цели вверх, одновременных не больше
  `FLOATER_LIMIT` (на телефоне `FLOATER_LIMIT_MOBILE`); при переполнении
  отбрасывается новое, а не вытесняется старое. Спрятанная вкладка
  (`document.hidden`) очередь чистит.
- Спрайты и фоны — ДАННЫЕ (`data/sprites.ts`): путь, автор, лицензия,
  «архетип моба → спрайт», «полоса уровней → фон». Сейчас это цветные
  силуэты-заглушки, но реестр настоящий и держится `content:check`: файл
  существует, у каждого архетипа из пулов зон есть спрайт и нет мёртвых
  строк маппинга, полосы фонов идут подряд с первого уровня без дыр и
  нахлёстов. Босс идёт своим силуэтом независимо от архетипа, неизвестный
  архетип — запасным.
- Позы для эталонов: `?debug=1&state=<пресет>&pose=<idle|swing|hit|crit|heal|rest>`
  застывают на пике эффекта и сравниваются с эталоном попиксельно — 2D это
  позволяет. Без пресета `pose` не работает: в живой игре застывшая поза
  была бы ложью о бое.
- Цвета сцены — из `ui/tokens.css` через `var(--…)`, как у любого компонента;
  второго набора цветов у игры нет. Что НЕ из токенов — сами спрайты и фоны:
  это картинки-ассеты, а не величины интерфейса, тот же довод, что и у
  цветов редкостей в `data/rarity.ts`.
- Бюджеты закреплены тестами (`tests/budgets.spec.ts`): за полчаса игрового
  времени узлы DOM не растут больше чем на 5% — для сцены из обычных
  элементов это и есть весь бюджет памяти, спрайты и числа — тоже узлы; при
  `document.hidden` всплывающих чисел не создаётся; тяжёлое меню не роняет
  кадры против лёгкого.
- ТРЁХМЕРНОГО СЛОЯ В ПРОЕКТЕ НЕТ. Он удалён целиком: `render3d/`, three,
  загрузчик моделей, GLB-ассеты и реестр клипов. С ним ушло около 200 кБ
  сжатого бандла и 8.5 МБ моделей. Библиотеку такого веса обратно не пускает
  CI: джоб `build` держит порог основного куска (900 кБ), и движок его
  пробивает сразу. Возвращать 3D — отдельное решение владельца, не правка.

## Скриншоты и визуальная регрессия

- `?debug=1&state=<пресет>` грузит заранее заданное состояние из
  `game/__fixtures__/presets/` и НЕ запускает игровой цикл: снимок обязан
  быть воспроизводимым до пикселя. Без `?debug=1` параметр не работает,
  неизвестное имя откатывает к обычной игре, а не к пустому экрану.
- Пресет — обычный сейв, поэтому читается той же цепочкой миграций, что и
  сейв игрока. Собираются они настоящими функциями игры (`build.ts`), так что
  застыть в невозможной форме не могут.
- Сид случайности в сейве НЕ хранится, поэтому режим съёмки пришивает свой
  (`SCREENSHOT_SEED`) и заново спавнит моба: иначе каждая загрузка давала бы
  другого противника и другую высоту страницы.
- Поверх пресета прокручивается `SCREENSHOT_TICKS` тиков — иначе лог боя пуст
  и снимок выглядит как сломанная игра. Число входит в определение эталона.
- Анимации выключены глобально под `prefers-reduced-motion` (Playwright
  открывает страницу именно так), живая полоска витрины при этом замирает.
- ДВА РЕЖИМА СЪЁМКИ, и ОБА сравниваются с эталонами попиксельно.
  `?scene=off` убирает боевую сцену и оставляет интерфейс с текстовой
  панелью: снимки меню от сцены не зависят. Без `scene=off` снимается
  тот же экран с двумерной сценой — она рисуется обычными элементами и
  векторными спрайтами тем же растеризатором, что и остальная страница,
  поэтому воспроизводима до пикселя. Прежний запрет сравнивать сцену
  относился к WebGL и ушёл вместе с ним.
- ПОЗЫ СЦЕНЫ — отдельный комплект эталонов: `?pose=<idle|swing|hit|crit|heal|rest|levelup>`
  на пресете `rich` застывает на пике эффекта. Это эталоны на САМИ ЭФФЕКТЫ,
  а не на раскладку: разъехался замах или крит — падает свой снимок с
  понятным именем.
- Эталоны — `tests/screenshots/`: интерфейс — три пресета × три ширины
  (390/768/1280), ВОСЕМЬ МЕНЮ × две ширины (390/1280), кукла с подсвеченным
  слотом во время выбора находки и витрина; сцена — три пресета × две ширины
  (390/1280; у сцены ровно две пропорции, 768 повторил бы 1280), семь поз на
  1280, сжатая сцена при открытом меню и строка-сводка вместо неё на 390.
  Меню снимаются на пресете `rich` — на нём ни одно из них не выглядит пустым.
- ЭЛЕМЕНТЫ С ЧИСЛАМИ СОСТОЯНИЯ СНИМАЮТСЯ ОТДЕЛЬНО И БЕЗ ДОПУСКА
  (`numeric-*`, список — `tests/numeric-elements.ts`). Полная страница
  сравнивается с долей 0.001 пикселей — иначе чужое сглаживание роняло бы
  каждый снимок, — но цифра в полоске здоровья это сотые доли процента
  пикселей страницы, и подмена «312 / 640» на «298 / 640» проходит сквозь
  такой порог незамеченной: два PR подряд так и подменили эталоны, а
  проверка молчала. Новый числовой элемент — ОДНА СТРОКА в списке; спека
  сама снимет его на `fresh` и `rich` при 1280.
- Требования, которые картинка не проверяет, проверяются измерением: на 320px
  `scrollWidth - clientWidth <= 0` (ничего не вылезает по горизонтали) и
  каждая кнопка меню не ниже 44px.
- Оба комплекта пишутся в `test-results/current` ДО сравнения и уходят
  артефактом при любом исходе: «посмотреть игру до merge» не должно зависеть
  от того, сошлись эталоны или нет.
- ЧТО ЛОВИТ КАРТИНКА, А ЧТО НЕТ: пиксельное сравнение ловит вёрстку, размеры
  и начертание, но НЕ ловит цвет — цветной текст занимает сотые доли процента
  пикселей страницы, и порога, который поймал бы его и пережил чужое
  сглаживание, не существует. Палитру и шкалы стережёт точный снимок токенов
  `tests/tokens.spec.ts` — он падает от любого изменения значения в
  `tokens.css` и показывает, что именно поменялось.
- Версия `@playwright/test` закреплена ТОЧНО: от неё зависит сборка Chromium,
  а значит и отрисовка. Разъедется версия — эталоны начнут врать. Поэтому же
  в CI берётся браузер из кеша Playwright, а НЕ системный chromium раннера:
  «не качать лишний раз» решается кешем, а не другой сборкой.

## Golden-тест

`src/lib/game/__tests__/golden.test.ts` прогоняет час симуляции с фиксированным сидом
и сравнивает снимки с эталоном `__snapshots__/golden.json`. Он ловит непреднамеренные
изменения игровых чисел: упал golden — рефакторинг изменил поведение, чини код.
Если PR меняет баланс осознанно — удали эталон, прогони тест дважды, закоммить новый
`golden.json` в том же PR и объясни в описании PR, что изменилось и почему.

## Как проверяется работа

У владельца проекта нет локальной среды и нет превью. Игра видна только по адресу
https://Peppapiggreedy.github.io/idle-rpg/ после merge. Поэтому в конце каждого ответа
пиши раздел «Как проверить» — 2–4 конкретных действия на живой странице и что должно
быть видно.
