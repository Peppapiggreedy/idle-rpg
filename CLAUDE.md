# Проект: Idle RPG — браузерная idle RPG

Idle/incremental RPG в духе классических MMORPG. Все названия, зоны, классы, предметы,
лор — **оригинальные**. Категорически запрещено использовать IP Blizzard: названия зон,
мобов, предметов, рас, классов, боссов и локаций из World of Warcraft, а также любые
их ассеты. При сомнении — придумывай своё.

## Стек

- Vite + Svelte + TypeScript
- Боевая сцена — двумерная, обычными элементами страницы (`src/lib/render2d/`).
  Движка нет: ни three, ни WebGL, ни канвы — сцена заводится в любом браузере
- break_infinity.js (класс `Decimal`) — для неограниченно растущих игровых величин
- Сохранение: localStorage, JSON, обязательное поле `version`
- Деплой: GitHub Actions → GitHub Pages, `base: '/idle-rpg/'`

## Команды

- Установка: `npm ci`
- Сборка: `npm run build`
- **Быстрый набор: `npm run test`** — типы, юниты, golden, проверка контента.
  Ни одного обращения к браузеру, ни одной матрицы прогонов. Около полутора
  минут. ВСЁ, ЧТО СТРОИТ ЭТАЛОННОЕ ПРОХОЖДЕНИЕ ИЛИ ГОНЯЕТ СИМУЛЯЦИЮ ПО
  ЛЕСТНИЦЕ, живёт в дорогом наборе, а не здесь: такие тесты стоят минутами,
  и один из них съедает быстрый набор целиком.
- Прогон баланса целиком: `npm run test:balance` (полная матрица плюс
  прогон полного пути и таблица обгона зон, ~45 минут на одном ядре)
- Прогон баланса выборкой: `npm run test:balance:sample` (~2 минуты)
- Визуальная регрессия: `npm run test:visual` (сборка + скриншоты, ~6 минут)
- Всё вместе: `npm run test:all`
- Проверка контента отдельно: `npm run content:check`
- Проверка типов отдельно: `npm run check`
- Обновить эталоны скриншотов: `npm run screenshots:update` (ВСЕ разом)
- Обновить ОДИН эталон: `npm run screenshots:update:one -- "имя снимка"`.
  Именно им и надо пользоваться: полное обновление, запущенное ради одного
  уехавшего снимка, заодно узаконивает все остальные — включая настоящую
  регрессию, которую тогда уже никто не найдёт. Список имён —
  `npm run screenshots:list`.
- Перегенерировать пресеты состояний: `npm run presets:update`

## Какие проверки когда

Наборы разделены по СТОИМОСТИ, и правило простое: во время работы гоняется
только дешёвый, дорогие — один раз в конце.

- **Во время работы — только `npm run test`, сколько угодно раз.** Он держится
  в пределах минуты и ловит почти всё: типы, юниты, golden, ссылки в данных.
- **Полный набор — ОДИН раз перед созданием PR**, а не после каждой правки.
  Прогонять матрицу баланса и скриншоты по кругу — это часы ожидания за день.
- **PR, трогающий `data/balance.ts`, кривые или формулы боя, обязан прогнать
  `npm run test:balance` ЦЕЛИКОМ и приложить таблицу в описание.** Выборки
  здесь мало: она проверяет три зоны из двадцати, а кривая ломается как раз
  на тех, что в выборку не попали.
- **Быстрый набор — минимум, ниже которого опускаться нельзя никогда.** Ни
  одна правка не уходит в PR, не пройдя `npm run test`.

Выборка (`BALANCE_SAMPLE=1`) сужает ОХВАТ, а не строгость: пороги, сравнения
и ассерты те же самые, просто зон три вместо двадцати, уровней два вместо
пяти, класс один и часов вчетверо меньше.

CI повторяет это разделение: типы, юниты, контент, баланс и снимки идут
ПАРАЛЛЕЛЬНЫМИ джобами, баланс и снимки — только если тронуто то, что их
касается (`src/lib/data/`, `src/lib/game/` для баланса; `src/lib/ui/`,
`src/lib/render2d/`, `App.svelte`, стили для снимков). Метка `full-checks`
на PR включает оба принудительно и переводит баланс на полную матрицу.
Ночью на `main` идёт `test:all` без выборок: красный ночной прогон означает,
что виноват один из мержей прошедшего дня.

## Архитектура

- `src/lib/game/` — логика: состояние, конвейер тика, формулы, лут, сейв, rng.
  Не знает про Svelte и рендер.
- `src/lib/stores/` — Svelte stores; состояние меняется ТОЛЬКО через экшены здесь
- `src/lib/ui/` — Svelte-компоненты; весь текст для игрока живёт тут.
  `ui/tokens.css` — дизайн-токены, `ui/kit/` — примитивы без знания о состоянии
- `src/lib/data/` — статические данные и баланс в отдельных файлах
- `src/lib/types/` — типы и интерфейсы

## Железные правила

- Игровая логика НЕ знает о рендере и не трогает DOM. Платформенные API
  (requestAnimationFrame, localStorage, Date.now) в `game/` допустимы только через
  инжектируемые параметры с браузерными дефолтами — чтобы логика тестировалась в node.
- Состояние меняется ТОЛЬКО через экшены в `stores/game.ts`. Чистые функции и
  константы компоненты могут импортировать из `game/` и `data/` напрямую.
- `Decimal` обязателен для величин, растущих неограниченно: золото, урон, опыт, HP,
  уровни, счётчики покупок. НЕ применяется к вероятностям, весам рулетки,
  миллисекундам и служебным счётчикам — это обычные `number`.
- Никаких накопительных мутаций игровых величин: любое изменение статов выражается
  источником (уровень, количество апгрейдов, надетые предметы), из которого значение
  пересчитывается конвейером `game/stats.ts`. Итоговые статы меняются ТОЛЬКО
  добавлением/удалением модификатора — прямых полей урона в состоянии нет.
- НИКАКИХ ВЕТВЛЕНИЙ ПО КОНКРЕТНОМУ ID в логике: ни `if (талант === '...')`,
  ни `if (класс === '...')`, ни `if (зона === '...')`, ни по id умения, данжа
  или задания. Поведение включается ФЛАГОМ, а его числа лежат payload'ом
  в данных рядом с флагом. Иначе новая сущность требует правки логики —
  и правило «контент добавляется только данными» перестаёт работать.
  Держится grep-тестом по `src/lib/game` — `game/__tests__/rules.test.ts`.
  Он же держит ещё три правила отсюда: баланс только в `data/`, текст для
  игрока не в логике, случайность только через `rng.ts`. Исключения там
  перечислены поимённо и с причиной, и каждая проверка проверена на заведомо
  битом образце.
- Весь игровой баланс живёт в `src/lib/data` (общий — в `data/balance.ts`), а не
  хардкодом в логике или компонентах.
- ЛЮБАЯ новая сущность — зона, моб, предмет, талант, умение, данж, спрайт,
  иконка — добавляется ТОЛЬКО правкой в `src/lib/data` и обязана пройти
  `npm run content:check`. Проверка держит ссылки (данж → зона, талант →
  умение, спрайт → файл, иконка → symbol в спрайте), достижимость (в каждую
  зону есть путь, каждый предмет выпадает, до каждого таланта хватает очков),
  обязательные `id`/`name`/`icon` с уникальными id и диапазоны чисел.
  Схемы — `data/__tests__/schema.ts`, там же образцы битых данных, на которых
  проверено, что проверка вообще срабатывает. Новый ТИП данных — новая схема
  и строка в списке покрытия в `integrity.test.ts`.
- В `src/lib/game` нет текста для игрока — только структурированные события и коды;
  рендерит их UI.
- Любая случайность — только через `game/rng.ts` (`createRng`). `Math.random`
  в `src/lib/game` запрещён.
- Никаких `setInterval`/`setTimeout` внутри Svelte-компонентов для игровой логики —
  есть один общий игровой цикл.
- Формат сейва имеет `version`. Меняешь структуру сейва — поднимай версию, пиши функцию
  миграции и тест на загрузку сейва прошлой версии. Прогресс игрока терять нельзя.
- Один PR = одна фича. Не рефактори то, о чём не просили.
- Коммиты в стиле Conventional Commits (`feat:`, `fix:`, `chore:`). Никогда не коммить
  в `main` напрямую — только ветка + PR.
- Нетривиальные игровые формулы комментируй одной строкой: что считает и почему.

## Классы

- ОСНОВНОЙ КЛАСС ОДИН — СТРАЖ (мана), и до альфы он такой один. Готовность
  класса лежит в ДАННЫХ (`status` у `ClassDef` в `data/classes.ts`):
  `ready` — по нему считаются контракты, `preview` — выбирается и играется,
  но нигде не заявляется как сбалансированный. Изувер — `preview`.
- ВСЕ КОНТРАКТЫ БАЛАНСА — темп, цена боя, убийств на уровень, кран золота,
  обгон зон, цена схватки с боссом, смертность, прогон полного пути —
  СЧИТАЮТСЯ ПО ГОТОВЫМ КЛАССАМ с автокастом по умолчанию. Golden и эталон
  полного пути — тоже по Стражу (`DEFAULT_CLASS` — первый готовый класс).
  Двойных прогонов «по обоим классам» не возвращать: контракт, который
  обязан сходиться на недонастроенном классе, либо роняет прогон впустую,
  либо заставляет крутить баланс класса, который ещё не проектировали.
- Тесты превью-класса ОСТАЮТСЯ, но некритичны: `classIt(cls)` из
  `game/__tests__/class-set.ts` для `preview` превращает провал в
  `console.warn` с пометкой `[превью]` в имени теста. Список классов для
  прогона — `contractClasses(sample)`: готовые первыми, в выборке только
  первый готовый. Новый контракт по классам пишется ТОЛЬКО через них, а не
  через `it.each(CLASSES)`.
- Хотя бы один класс обязан быть `ready` — держит `content:check`: иначе не
  по кому считать контракты и некуда мигрировать старые сейвы.
- На экране выбора класса превью-класс НЕ ПРЯЧЕТСЯ: карточка на месте, с
  пометкой «В разработке» и одной строкой о том, что баланс не настроен.
  Текст, как и весь текст для игрока, живёт в UI (`ui/ClassPicker.svelte`).
- Когда Изувер будет настроен, переключение — одна правка данных:
  `status: 'ready'`. Логика и тесты про это не знают.

## Статы

- Конвейер `game/stats.ts` — единственный источник производных чисел. Порядок
  СТРОГО: `base -> +Σflat -> ×(1+Σpercent, аддитивно) -> ×Πmultiplier`.
- Четыре базовые характеристики — сила (урон), ловкость (скорость и криты),
  интеллект (мана), живучесть (здоровье) — обычные статы конвейера; их итоги
  сам конвейер разворачивает во вклады в производные статы плоскими
  модификаторами `attribute:<имя>` (ставки — в `data/balance.ts`). Прогрессия
  героя — предметы (у предмета есть УРОВЕНЬ, сила растёт от него линейно)
  и таланты, плюс небольшой прирост характеристик за уровень.
- Модификатор `kind: 'base'` ЗАМЕНЯЕТ дефолт из `data/balance.ts`, а не прибавляется.
  Контракт — ровно один base-источник на стат (оружие задаёт `weaponSpeed`); если
  их несколько, выигрывает последний в порядке `collectModifiers` (закреплено тестом).
- Скорость атаки — ДВЕ разные величины, имя `attackSpeed` запрещено:
  `weaponSpeed` — секунд между ударами (меньше = быстрее, база из `UNARMED`),
  `haste` — доля ускорения (больше = быстрее, старт 0).
- `swingTime = weaponSpeed / (1 + haste)` — производная, её нет среди `StatId`:
  модификатор на неё выдать нельзя, только на `weaponSpeed` или `haste`.
- Прогресс замаха хранится ДОЛЕЙ `0..1`, а не в миллисекундах: при смене оружия
  или haste доля сохраняется сама — ни сброса удара, ни мгновенного, ни эксплойта
  на переодевании. Пересчитывать её при изменении `swingTime` не нужно.
- У мобов оружия нет: в данных лежит `swingTime` напрямую.

## Экипировка

- Слоты — данные (`data/slots.ts`), не хардкод в логике. Шаблоны предметов —
  `data/items.ts`.
- СТАРТОВЫЙ КОМПЛЕКТ — ОДНО БЕЛОЕ ОРУЖИЕ, шесть слотов пусты. Тир лежит в
  данных класса (`rarity` у `StartingItem`), а не в коде. Полный редкий
  комплект прежней версии не давал запуститься главной петле игры: почти
  любая находка была хуже подарка, и значок «Апгрейд» не загорался часами.
- ПУСТОЙ СЛОТ — ЭТО НОЛЬ, и порог апгрейда для него другой: вещь не обязана
  оценку ПОДНЯТЬ, ей достаточно её не уронить. Мера «лучше» одна на всю игру
  (убийств в секунду), а живучесть входит в неё только через аптайм — там, где
  герой не умирает, первый в жизни панцирь оценку не двигает вовсе, и игра
  сказала бы «не апгрейд» о вещи на голое место.
- НА ВЫПАДАЮЩИХ И КОВАНЫХ ВЕЩАХ ТОЛЬКО ПЛОСКИЕ ПРИБАВКИ. Процент считается
  от суммы конвейера, то есть от остальной экипировки: такой предмет нельзя
  оценить сам по себе, а сравнение находок поштучное. И он не растёт ни от
  уровня вещи, ни от тира — множитель силы умножает плоское, а проценту
  умножать нечего. Проценты живут в зачарованиях, талантах и зельях.
  Держится проверкой контента.
- У всего, что идёт в руки, есть ХВАТ (`grip` в шаблоне): `'one'` — в любую
  руку, `'two'` — обе руки, `'shield'` — только вторая. Одно поле, а не два
  флага: щитом и оружием одновременно быть нельзя. Хват берётся ИЗ ШАБЛОНА
  и отдельным броском не разыгрывается; проверяется схемой в `content:check`.
- Правила хвата живут в `game/equipment.ts` (`equipStatus`) и возвращают КОД
  отказа — `two-handed-needs-both`, `shield-offhand-only`,
  `occupied-by-two-handed`. Текст причины рендерит UI, как у умений.
  Двуручное само снимает вторую руку В СУМКУ; сумка полна — отказ кодом,
  а не молчаливая потеря предмета.
- У предмета есть `slot` и `mods` — массив модификаторов в формате `stats.ts`.
  Никаких «прибавок к урону» отдельным полем: предмет действует ТОЛЬКО через
  конвейер статов.
- Главный атрибут брони К СЛОТУ НЕ ПРИВЯЗАН: его разыгрывает лут
  (`ARMOR_ATTRIBUTES`, ровные веса), у кованого он задан в данных рецепта.
  Эталон прогона берёт матожидание (`averageArmorMods`) — четверть бюджета
  в каждый атрибут.
- Оружие задаёт БАЗУ боя: `weaponSpeed`, `weaponDamageMin`, `weaponDamageMax`
  тремя модификаторами `kind: 'base'` с `source: 'equipment:weapon'`. Сняли —
  значения вернулись к `UNARMED` из `data/balance.ts`. Побочные статы оружия
  (сила атаки, крит, haste) — ОБЫЧНЫЕ модификаторы, не base.
- Надетый предмет продать нельзя — сперва снять (`sellItem` проверяет явно).
- Сравнение предметов и автонадевание — только по оценочному урону в секунду
  из `estimateCombatRate`, никогда по сумме статов.
- ОЦЕНКА — ДОЛГОСРОЧНОЕ СРЕДНЕЕ, А НЕ ОДИН ЦИКЛ. `estimateCombatRate`
  описывает сотни боёв за час, поэтому целых чисел одного цикла в ней нет:
  удары на моба, ответные удары за бой и бои до привала — дробные
  матожидания («целое, усреднённое по фазе» = дробное плюс половина), а
  смерть в цикле — вероятность, а не флаг (`farmCycle`, разброс цены боя
  `FIGHT_COST_SPREAD`). Прежние `floor`/`ceil` делали метрику ступенчатой:
  единица силы атаки перекидывала цикл с привала на смерть и роняла темп
  убийств втрое, а сравнение предметов выбирало худшее (откат `4a000e4`).
  Держится тестом `rate-continuity.test.ts`: по мелкой сетке каждого стата
  силы `killsPerSecond` не убывает, а шаг между соседями не больше
  `RATE_CONTINUITY_MAX_STEP` от наибольшего. Новый `floor`/`ceil` в
  `rawRate` или `farmCycle` — это регрессия, а не уточнение.

## Умения

- Умения — данные (`data/abilities.ts`): `manaCost`, `cooldown`,
  `weaponDamagePercent`, `triggersGcd`, `unlockLevel`, опциональный `effect`.
- Умения открываются УРОВНЯМИ (`unlockLevel`): у каждого класса ровно одно
  умение первого уровня, дальше по одному — держит схема данных. Запертая
  кнопка видна с причиной, автокаст запертые пропускает.
- Урон умения — ДОЛЯ УДАРА ОРУЖИЯ (`weaponDamagePercent`), а не множитель
  к силе атаки: иначе умения перестанут масштабироваться от оружия. Считает
  их та же `rollSwing` из `combat.ts` — своей формулы у умений нет.
- Два типа. `instant` бьёт сразу, тратит GCD и НЕ трогает прогресс замаха.
  `onNextSwing` встаёт в очередь и заменяет следующую автоатаку: GCD не
  тратит, отменяется повторным нажатием, мана списывается В МОМЕНТ УДАРА.
  Одновременно в очереди только одно `onNextSwing`.
- Кулдауны и GCD идут ИГРОВЫМ временем (тем же `dtMs`), поэтому множитель
  скорости из отладочной панели ускоряет и их.
- Каждый отказ — отдельный код (`locked`/`dead`/`cooldown`/`gcd`/`no-mana`)
  из `abilityStatus`; текст причины рендерит UI.
- Очередь и наложенные эффекты живут на КОНКРЕТНОМ мобе: его смерть, респаун,
  смерть героя и загрузка сейва их снимают.

## Данжи

- Данж — данные (`data/dungeons.ts`): вход из конкретной зоны,
  `unlockRequirement`, цепочка боссов в ФИКСИРОВАННОМ порядке и `opensZoneIds`
  — РОВНО ДВЕ зоны, которые открывает первое прохождение.
- ЦЕНА СХВАТКИ С БОССОМ — ОКОЛО 80% ЗАПАСА героя, хорошо одетого для своего
  уровня (замер: 69-89%, в среднем 79). Это отдельный контракт, рядом с
  контрактом цены обычного боя, и держится он тестом на настоящем тике.
- МЕЖДУ БОССАМИ ЕСТЬ ПРИВАЛ, и он несёт предыдущий пункт: три схватки по 80%
  на одном запасе не проходятся никак. Каждая ступень цепочки начинается с
  полной полоски, поэтому и мерить цепочку надо схваткой, а не суммой.
  После ПОСЛЕДНЕГО босса привала нет — отдыхать не от чего, герой выходит.
  На привале СТОИТ СЧЁТЧИК ЯРОСТИ и не выходит следующий босс: иначе герой
  возвращался бы к противнику, разъярённому на всю длину отсидки.
- УРОН БОССА ПАДАЕТ ОТ ПЕРВОГО К ТРЕТЬЕМУ (1.48 → 0.99 → 0.76 от урона
  обычного моба того же уровня), и это арифметика равной цены, а не «третий
  слабее»: запас HP растёт по цепочке в 1.7 раза, схватка ровно во столько же
  длиннее, значит урон в секунду обязан упасть. Опасность третьего босса —
  в ДЛИНЕ боя: отметка ярости у него ближе к пределу.
- ДАНЖ — ЖЁСТКИЕ ВОРОТА, и требовательность растёт по тиру: первый берётся
  82% доступной экипировки, восьмой требует 96% (`requiredGearShare` = 80 +
  2×тир). Проверяется В ОБЕ СТОРОНЫ: с положенной долей цепочка проходится,
  с долей на 15 пунктов ниже — нет. Односторонняя проверка пропустила бы
  данж, который проходится всегда, то есть перестал быть воротами.
  Лестница ВЫСОКАЯ И УЗКАЯ (было 60-95%) именно из-за цены схватки: если
  босс снимает 80% с хорошо одетого, то плохо одетого он снимает целиком.
- Босс — не отдельная сущность: та же `buildMonster`, что и у мобов, только
  роль умножена на `hpMult`/`damageMult`/`goldMult`/`xpMult`. Своей формулы
  у боссов нет.
- Лут босса — свой пул (`loot.slots` + `minRarity`), качество растёт от
  первого босса к третьему. Падает целиком, а не по общему шансу дропа.
- Ярость: после `enrageAfterSec` урон растёт на `ENRAGE_GROWTH` каждые
  `ENRAGE_STEP_SEC`. Это проверка на урон в секунду и ЗАЩЁЛКА ДЛЯ СИЛЬНО
  ОТСТАВШИХ, а не главный убийца. Пока схватка стоила десятой доли запаса,
  обычные удары не убивали никого и дожимала только отметка; при цене в 80%
  герой, который тянет схватку в полтора раза дольше, не доживает до отметки
  и без неё. Не пытайтесь вернуть «обычные удары герой переживает всегда» —
  это прямо противоречит цене схватки.
- Смерть внутри выкидывает наружу и стирает прогресс цепочки; лут за уже
  убитых боссов остаётся. Добровольный выход — то же самое.
- Первое полное прохождение поднимает флаг в `dungeonsCleared` — РОВНО один
  раз — и даёт постоянный бонус к опыту.
- Цепочка боссов сама себя не проходит: оффлайн-агрегат внутри забега не
  считается. Что происходит с забегом при загрузке сейва — ниже, общим
  правилом для всего закрытого контента.

## Храм испытаний

- Храм КОНЕЧЕН: `floors` в `data/temple.ts`. Без потолка «полная зачистка»
  недостижима, а с ней недостижимы и награда за неё, и честное «награды
  исчерпаны» на входе.
- КУЛДАУНА НЕТ. Заходить можно сколько угодно; фарм закрыт не запретом, а
  построением: платят только этажи ВЫШЕ рекорда, а рекорд нельзя побить
  дважды. Рекорд — максимальный ПОЛНОСТЬЮ пройденный этаж, лежит в сейве.
- Награда за этаж — пыль и золото, числа в данных (`floorReward`), растут по
  этажам. За полную зачистку СВЕРХУ и ровно один раз: токен для преквеста
  рейда и уникальный рецепт; повторная зачистка их не дублирует (флаг
  `templeCleared`, а не «рекорд равен потолку»).
- СМЕРТЬ ЗАСЧИТЫВАЕТСЯ. Это завершение забега с результатом: этаж, на котором
  героя добили, пройденным не считается (его отмечает смерть БОЙЦА), а все
  этажи под ним оплачиваются и поднимают рекорд. Добровольный выход — то же
  самое.
- ПРЕРЫВАНИЕ НЕ ЗАСЧИТЫВАЕТСЯ, и это ДРУГОЙ путь. Закрытая вкладка
  расформировывает забег общим правилом (`resumeOutside`): рекорд не меняется,
  награды не выдаются. Разводит их последний аргумент `leaveTemple(credit)`.
  Пойди смерть по ветке прерывания — погибнуть стало бы не дороже, чем
  закрыть вкладку, и риск смерти вместе с привалом потерял бы смысл.
- НАГРАДА ЗА ХРАМ — ЭТАЖИ, А НЕ МОБЫ. Бойцы храма не дают ни опыта, ни
  золота, и лут внутри не падает. Замер до правки: храм на семидесятом
  уровне давал 386 578 опыта в час против 249 266 в подходящей зоне и больше
  убийств, то есть и бросков лута. Кулдауна нет — храм стал бы лучшей фермой
  в игре.

## Прерванные забеги

Общее правило для ВСЕГО закрытого контента: данжа, храма и будущего рейда.
Отдельной ветки на каждую активность быть не должно — правило держится в
одной точке (`resumeOutside` в `game/save.ts`).

- Прерванный забег ПРИ ЗАГРУЗКЕ СЕЙВА расформировывается: прогресс цепочки
  сброшен, лут за уже убитых боссов остаётся, герой выходит наружу в
  подходящую по уровню зону, и оффлайн начисляется ПО НЕЙ. Закрыв игру в
  любой момент, игрок не должен возвращаться к пустому экрану.
- Сама попытка при этом НЕ продолжается в оффлайне и НЕ засчитывается —
  забег придётся начать заново. Это ДВА РАЗНЫХ СВОЙСТВА, и путать их нельзя:
  первое — про то, что время не пропало; второе — про то, что данжи не
  проходятся закрытой вкладкой.
- Зону выхода выбирает одна детерминированная функция (`offlineZone` в
  `game/zones.ts`), строго в этом порядке: последняя выжитая, если её мобы
  в пределах `gap <= 5`; иначе самая высокая открытая зона, где герой не
  гибнет и мобы не отстали; иначе безопасная.
- Модалка возврата НАЗЫВАЕТ это вслух: из чего вышел и по какой зоне
  начислено. Молча пропавшая цепочка читается как потеря прогресса.
- При входе в закрытую активность UI предупреждает одной строкой
  (`ui/runText.ts`), что закрытая вкладка прервёт забег, но оффлайн будет
  начислен. Строка снимает главный страх и стоит копейки.

## Таланты

- Дерево — данные (`data/talents.ts`): у каждого класса три ветки по 13
  этажей глубиной `BRANCH_DEPTH` = 61 очко; у таланта `branch`, `row`,
  `maxRank`, `requiredPointsInBranch` и `effect`.
- Эффект бывает ДВУХ видов и только двух: массив модификаторов конвейера
  статов (`source: 'talent:<id>'`, значение множится на ранг) либо ФЛАГ,
  включающий поведение. Ни одного `if (талант === '...')` в логике: флаг
  описан в данных вместе со своим payload.
- Очко за уровень начиная с `TALENT_FIRST_LEVEL`. Доступные очки — всегда
  производная (`заработано − вложено`), отдельного счётчика в состоянии нет.
- Правила вложения — в `game/talents.ts`, каждый отказ отдельным кодом
  (`no-points`/`max-rank`/`branch-locked`); текст причины рендерит UI.
- Сброс за золото, цена растёт от `talentResets`. Сброс обнуляет ранги
  и пересчитывает статы.
- Таланты ускорения выражаются модификатором `haste` и НИКОГДА плоской
  прибавкой к `weaponSpeed`: иначе один талант увёл бы скорость оружия
  в ноль или в минус, а `swingTime` — в бесконечность. Ускорение живёт
  в долях, поэтому «+10% скорости» — это `{ stat: 'haste', kind: 'flat',
  value: 0.1 }`, а не `percent` (процент от нуля даёт ноль). Источник
  модификатора на итог не влияет — закреплено тестом «талант на +10% haste
  даёт тот же swingTime, что и предмет на +10% haste», а запрет на
  `weaponSpeed` в талантах — отдельным тестом по данным дерева.

## Автокаст

- Настройки автокаста — часть состояния и сейва: галка `autocast` и `priority`
  на каждое умение. Автокаст жмёт ПЕРВОЕ доступное по приоритету, у которого
  хватает маны и вышел кулдаун.
- Разница между авто и рукой возникает ЕСТЕСТВЕННО, из ровно двух правил:
  задержка реакции `AUTOCAST_DELAY_MS` после того, как умение стало доступно,
  и то, что автокаст не придерживает кулдауны (добивает моба крупным умением,
  урон уходит в перебой). Множителей «за автоматизацию» нет и быть не должно.
- Потолок отставания `AUTOCAST_MAX_LOSS` — это СНЯТИЕ лишнего штрафа, а не
  добавление нового; точка отсчёта — та же ротация, сыгранная руками.
- ЖЕЛЕЗНОЕ ПРАВИЛО: `оффлайн <= автокаст <= ручная игра`. Оффлайн считается
  по модели автокаста (та же задержка и приоритеты) и режется на
  `OFFLINE_EFFICIENCY`. По идеальной игре оффлайн не считается никогда.
- `estimateCombatRate(state, mode)`: `'auto'` (по умолчанию) — что герой выдаёт
  сам, `'manual'` — что выйдет, если жать умения самому. UI показывает обе.

## Зоны

- Зоны — данные (`data/zones.ts`): `monsterLevelRange`, `monsterPool`,
  `rewardMultiplier`, `isSafe`. Ровно одна зона обязана быть `isSafe` — в неё
  возвращает смерть.
- ЗОНУ ОТКРЫВАЕТ ДАНЖ, А НЕ УРОВЕНЬ. Поля `unlockRequirement` у зоны НЕТ:
  требования шли тройками, а полосы мобов пятёрками, и последняя зона
  открывалась на 58 уровне при мобах 96-100. Двадцать зон раскладываются без
  остатка: четыре стартовых плюс восемь данжей по две. Ритм — десять уровней
  зоны, данж, десять уровней. Зона, которую не открывает ни один данж, открыта
  с начала игры (`INITIAL_ZONE_IDS`), и таких ровно четыре.
- Открытые зоны лежат в сейве ОТДЕЛЬНЫМ полем (`unlockedZoneIds`), а не
  выводятся из `dungeonsCleared`: «данж пройден» это достижение (постоянный
  бонус к опыту и уникальные награды), «зона открыта» — доступ. Миграция
  старых сейвов обязана вернуть зоны, не выдав достижений.
- Мобы не лежат в данных готовыми: `data/monsters.ts` хранит архетипы (роль)
  и ФОРМУЛУ масштаба от уровня. Числа hp/урона/наград считает `buildMonster`,
  логика их не выводит.
- `spawnMonster(zone, rng)` — броски строго: уровень из диапазона, затем
  архетип из пула.
- Опасность зоны НЕ пишется текстом в данных: `game/zones.ts` считает прогноз
  (`forecastZone`) через ту же `estimateCombatRate`, что и бой, и отдаёт код
  вердикта. Игроку вердикт НЕ показывается (см. «Экран и разделы»): им
  пользуются `offlineZone`, оффлайн-агрегат и тесты.
- Темп зоны (`zoneRate`) — среднее по ВСЕМ мобам, которых может выдать спавн
  (пул × уровни). Смертность считается один раз на зону по средней потере HP:
  запас HP у героя общий на всю череду боёв.
- Оффлайн идёт шагами по `OFFLINE_CHUNK_MIN`: набранные уровни меняют статы,
  а значит и темп следующего шага.
- ЛУТ В ОФФЛАЙНЕ ПАДАЕТ. Внутри шага по числу убийств крутится ТА ЖЕ
  `rollLoot` и ТА ЖЕ `stashLoot`, что в тике: второй модели дропа и второй
  копии правил сумки нет. Отдельного коэффициента у лута тоже нет — число
  убийств уже урезано на `OFFLINE_EFFICIENCY`. Уровень находки — по среднему
  мобу зоны, как и весь остальной агрегат. Автонадевания по-прежнему нет:
  герой возвращается к сумке находок.
- ШТРАФ ОПЫТА ЗА ОТСТАВАНИЕ считается по уровню КОНКРЕТНОГО МОБА
  (`gap = уровень героя − уровень моба`), а не зоны: зона накрывает пять
  уровней, и по её границе штраф врал бы половине пула. Ступени —
  `XP_GAP_PENALTY` в `data/balance.ts`, границы и коэффициенты живут там и
  двигаются только там.
- Штраф бьёт ТОЛЬКО по опыту. Золото, материалы, травы и лут не трогаются:
  отставшие зоны обязаны оставаться полезными для фарма низких материалов,
  иначе за ними будет некуда пойти. ЦЕНА ЭТОГО ПРАВИЛА ИЗМЕРЕНА: герой
  двадцатого уровня на стартовом лугу зарабатывает 106% того, что заработал
  бы в своей зоне. Предложение частичного штрафа золота лежит в
  `data/balance.ts` рядом со штрафом опыта — не применено, решение открыто.
- РАЗРЫВ В ДРУГУЮ СТОРОНУ — МОБ ВЫШЕ ГЕРОЯ — бьёт по ВХОДЯЩЕМУ УРОНУ:
  `levelGapDamageMult`, пять уровней бесплатно (ширина полосы зоны), дальше
  +30% за уровень. Ставкой роста урона это не заменяется: у линейных функций
  отношение соседних зон от ставки не зависит и с уровнем стремится к
  единице — резкой отсечки линейная кривая не даёт ни при каком числе.
  Контракт: герой уверенно держит зоны до +5 и с риском до +10, глубже никак.
- Штраф знают все, кто считает опыт во времени: начисление за убийство,
  `zoneRate` (а через неё прогноз зоны и оффлайн). Кривую стоимости уровня
  он НЕ трогает — она считается по зоне, куда игра ведёт героя, где разрыва
  нет по определению.
- Прогноз зоны отдаёт долю опыта полем `xpShare` (1 / 0.5 / 0) по среднему
  уровню мобов — тем же разрывом, что и `levelGap` рядом. Точное начисление
  идёт по каждому мобу, поэтому зона на границе ступени платит между двумя
  долями; настоящее число видно в `xpPerHour`. Текст рендерит UI.

## Цена боя

Рядом с контрактом темпа (TTK 8-15 секунд, `PACING` в `data/balance.ts`)
стоит второй, о цене той же схватки:

```
Герой уровня L в актуальном для L снаряжении теряет 9–15 %
максимального здоровья за один бой с МЕДИАННЫМ мобом своей зоны.
Нетто, с учётом регенерации. Действует с первого уровня, без скидок
на первые уровни. Числа коридора — FIGHT_COST_TARGET в data/balance.ts.
```

Коридор был 20–25 %: по живой игре это оказалось жестковато, и владелец снял
врагам пятнадцать процентов урона. Двигается он ОДНИМ числом —
`MONSTER_BASE.damage`; всё остальное (скидка ранних полос, множители боссов,
пороги тестов) считается от него.

КОРИДОР 9–15 % — ПЕРЕКАЛИБРОВКА ИНСТРУМЕНТА, А НЕ ИГРЫ (вторая ночь).
Прежние 13–20 % мерились моделью боя, которая не знала, что привал наливает
ману до полного, и считала бой на 15 % длиннее настоящего — а с ним и число
ответных ударов. Модель, сходящаяся с тиком в 3 % (девять замеров уровень ×
крит), даёт настоящую цену медианного боя: 10–14 %, в среднем 11 %. Тик
подтверждает: при пороге 0.6 герой уходит на привал после 3.7 боя, то есть
теряет по 11 % за бой. Игра при этом не менялась ни на число — менялась
линейка. Вернуть в игре 13–20 % значило бы поднять урон мобов на четверть,
то есть откатить решение владельца о минус пятнадцати; это его выбор, и он
записан открытым вопросом отчёта второй ночи.

ПЯТНАДЦАТЬ ПРОЦЕНТОВ УРОНА — ЭТО НЕ ПЯТНАДЦАТЬ ПРОЦЕНТОВ ЦЕНЫ, и коридор
приходится не только сдвигать, но и расширять. Цена боя — это `входящий минус
реген`, разность двух больших чисел: срезав входящий на 15 %, всю эту долю
снимаешь с разности, а она куда меньше. Замер по прежней модели: средняя
цена упала с 22 % до 16 %, то есть на четверть с лишним, и упала НЕРОВНО —
там, где реген занимает бо́льшую долю схватки, срез бьёт сильнее. Отсюда
шесть-семь пунктов коридора вместо пяти.

- ДВА КОНТРАКТА НА ОДНУ СХВАТКУ, и ручки у них разные: длину боя задаёт
  здоровье моба, цену — его урон. Правишь одно — второе не трогается.
- КОНТРАКТ СТОИТ НА ЭТАЛОННОМ ГЕРОЕ (`referenceBuild`, модель `equipUpgrades`),
  а не на формуле «урон моба = 22% запаса героя». Это разные вещи, и вторая
  убивает смысл живучести и брони: сколько их ни набирай, моб снимал бы ту же
  долю. Числа расходятся САМИ — снаряжение лучше эталона теряет меньше 20%,
  хуже эталона больше 25%, — и тест обязан проверять ОБА отклонения.
  Односторонний тест не отличает верную реализацию от этой подмены.
- МЕРИТСЯ НА ВХОДЕ В ЗОНУ, то есть на уровне, с которого игра в неё приводит.
  Внутри зоны доля падает сама: герой растёт пять уровней, а мобы стоят на
  месте. Это не дырка в контракте, а награда за то, что зону доигрывают.
- ДОПУСК ±2 ПУНКТА, и он не от лени. Цена боя — это `урон моба × число ударов
  за бой ÷ запас героя`, а число ударов целое: один лишний удар из шести-восьми
  двигает долю на два-три пункта. Сверху ложится ширина коридора темпа: бой
  на 15 секундах стоит на четверть дороже боя на 12, а оба законны. Замер
  по прежней модели: из сорока точек (двадцать зон × два класса) в 13-20%
  попадало тридцать восемь; по точной модели в 9-15% укладываются все
  двадцать зон Стража (10.2-14.4%). Сузить коридор цены можно только сузив
  коридор темпа, и это отдельное решение.
- ЦЕНА ХУДШЕГО БОЯ — ДРУГОЕ ЧИСЛО, и именно оно решает, гибнет герой или нет:
  здоровяк с верхнего края полосы стоит 14-38% запаса по модели (в стартовой
  зоне 38%; настоящий тик от шестнадцатого уровня даёт 16-20%). Прежние
  «20-42%» держались на модели без крита и с целым числом ответных ударов.
  Порог привала по умолчанию стоит ВЫШЕ него (см. `REST_HP_THRESHOLD_DEFAULT`).
- ЦЕНА БОЯ ЗАДАЁТ АПТАЙМ. При 13-20% за бой герой уходит на привал после
  второго-третьего убийства: модель зоны даёт 19-31% времени вне боя, полный
  путь 1..100 — 33% и 36% по классам (было 0.3-1.0%). Этот простой обязан
  быть в оффлайн-агрегате: он там и есть, через `uptime` из `farmCycle`, и без
  него оффлайн завысил бы добычу на треть. Простой от привала и простой от
  смерти — РАЗНЫЕ вещи, их различает поле `dies` у `zoneRate`; вердикт зоны
  смотрит на него, иначе любая зона читалась бы как смертельная.
- УБИЙСТВО ВИДНО СНАРУЖИ ПО ДВУМ ПРИЗНАКАМ, а не по одному: взведённый таймер
  респауна ИЛИ уход на привал. Решение об отдыхе принимается после убийства и
  до `applyRespawn`, и уход обнуляет таймер — считая только по нему, прогон
  недосчитывался почти сорока процентов убийств.

## Дизайн-система

- `ui/tokens.css` — ЕДИНСТВЕННЫЙ источник визуальных величин: палитра,
  шкала отступов (4/8/12/16/24/32), радиусы, тени, типографика, длительности,
  брейкпоинт. В компонентах не должно быть ни одного hex-литерала и ни одного
  отступа числом — только `var(--…)`. Держится тестом `ui/kit/kit.test.ts`.
- Тема ОДНА и тёмная. Переключалки светлой/тёмной нет и не будет: игра, в
  которую смотрят часами, отладочные оверлеи всегда были тёмными, а цвета
  редкостей на светлом фоне выцветают.
- Цветов редкостей в токенах НЕТ намеренно — они живут в `data/rarity.ts`
  вместе с весами рулетки. Компонент получает цвет через `--rarity-color`,
  который проставляет `ui/kit/rarity.ts`. Второго набора быть не должно —
  это тоже проверено тестом.
- Семантика цвета: `--c-damage` урон, `--c-heal` здоровье, `--c-mana` мана,
  `--c-xp` опыт и прокачка, `--c-gold` золото, `--c-warning` предупреждение.
  `--c-accent` — про ВЗАИМОДЕЙСТВИЕ (кнопка, фокус, наведение) и намеренно не
  совпадает ни с одной семантикой: «нажми меня» не должно путаться с «тут урон».
- Примитивы `ui/kit/`: `Panel`, `Button`, `StatBar`, `IconSlot`, `Tooltip`,
  `NumberText`, `Tag`. Они НЕ знают про игровое состояние — только пропсы.
  Компонент, который лезет в стор из примитива, сломал правило.
- Шрифт один — Inter, лежит в `public/fonts/` подмножествами кириллицы и
  латиницы. Из сети не тянется: страница выглядит одинаково везде и
  открывается без интернета. Табличные цифры включены глобально.
- Витрина `/ui` (только при `?debug=1`) показывает все примитивы во всех
  состояниях, всю палитру, все редкости и всю шкалу типографики на одной
  странице. Добавил примитив или состояние — добавь его туда же.

## Крафт

- ПОШЛИНА КРАФТА — ДОЛЯ ЧАСОВОГО ДОХОДА, а не число (`CRAFT_TOLL_HOURS` в
  `data/recipes.ts`): еда 0.125 часа, склянка 0.375, кованая вещь 1, уникум 2.
  Числом её пришлось бы держать в двух местах — в цене и в кривой золота, — и
  они разъехались бы на первой правке баланса. Зачарования пошлины не платят:
  они стоят пыль.
- Часовой доход берётся ТАМ ЖЕ, где кривая опыта берёт цену уровня: награда
  типичного моба своей зоны на убийства в час (`goldPerHourAt`). Второй модели
  дохода в игре нет, и совпадение модели с прогоном проверяется тестом.
- Уровень рецепта — «самый глубокий из самых мелких»: каждый вход стоит
  столько, сколько стоит мельчайшая зона, где он есть, а рецепт — столько,
  сколько стоит самый труднодоступный из входов. Иначе за луговой травой
  пришлось бы ходить на девяностый уровень.
- Цена видна ДО нажатия, кнопка заперта отказом с кодом (`gold`), текст рисует
  UI. Порядок отказов: уровень, запертость, материалы, золото, место в сумке.

## Прогон баланса

- `game/simulate.ts` — headless-симуляция: `simulate({ hours, zoneId, build })`
  крутит НАСТОЯЩИЙ конвейер тика N игровых часов и возвращает метрики
  (убийств/золота/опыта/смертей в час, время до следующего уровня, итоговый
  уровень). Своей модели боя у прогона нет — иначе он мерил бы не ту игру.
- Метрики считаются ТОЛЬКО по наблюдаемому снаружи состоянию: убийство — по
  взведённому таймеру респауна, смерть — по переходу `alive → dead`, каст —
  по подскочившему кулдауну, урон — по шине `AttackEvent`. Ради прогона в тик
  не добавлено ни одного счётчика.
- Билд задаётся источниками статов, как в игре: уровень, уровень вещей,
  надетое оружие, ранги талантов, галки автокаста. Автонадевание в прогоне выключено —
  иначе билд подменится на середине.
- `freezeLevel` держит героя на стартовом уровне: за час свободного прогона
  герой уходит на десятки уровней вперёд, и строка «уровень 1» на самом деле
  мерит уровни 1..30. Сравнивать зоны между собой можно только замороженными.
- Зона задаётся напрямую, без проверки открытости: это измерительный прибор,
  и «что будет, если сунуться раньше времени» — законный вопрос. Правило входа
  живёт в `travelToZone` и продолжает работать в игре. Герою прогона зоны
  проставляются моделью `unlockedByLevel`: он делает данж, когда тот
  открывается, — иначе прибор мерил бы героя, запертого в стартовой четвёрке.
- Эталонный герой одевается НЕ С ПЕРВОЙ СЕКУНДЫ: первую зону он проходит в
  стартовом комплекте (одно белое оружие) и переодевается на первом переезде.
  Полный средний комплект на первом уровне описывал бы героя, которого не
  существует, — против мобов стартовой зоны он быстрее настоящего вдвое.
- `game/__tests__/balance.test.ts` печатает таблицы и держит свойства баланса:
  прогресс монотонный по зонам, доминирующей зоны нет, десятый уровень с нуля
  берётся за 15–28 минут игрового времени, подходящая по уровню зона не убивает,
  три оружия с равным уроном оружия в секунду сходятся в пределах 3%.
- Инвариант «равный урон оружия в секунду — равный итог» держится там, где бой
  длится больше десятка замахов. Когда моб умирает с одного удара, лишний урон
  крупного замаха пропадает, и быстрое оружие выигрывает числом замахов —
  это перебой, а не поломанная нормализация. Отдельная таблица в тесте
  показывает, где проходит граница.
- Страница `/balance` (только при `?debug=1`) считает те же таблицы на лету.
  Числа пресета — `BALANCE_PRESET` в `simulate.ts`, общий для теста и страницы.
  Игровой цикл на этой странице не запускается: прибор не фармит за игрока.

## Экран и разделы

- «Игра называет, ЧТО сделать нельзя, и никогда — ЧЕМ КОНЧИТСЯ попытка.
  Ограничение словами, исход молчит. Игрок имеет право ошибиться.»
  Поэтому вердикт зоны (`forecastZone`: по силам / риск / смерть / не по
  зубам) в интерфейсе НЕ показывается — ни словом, ни цветом, ни иконкой;
  сама функция остаётся, ей пользуются `offlineZone`, оффлайн-агрегат и
  тесты. Прогноза схватки с боссом до входа в данж нет и не будет:
  ограничения по уровню, зоне, смерти и «уже внутри» — это «нельзя», а не
  «умрёшь». Факты показываются: полоса уровней мобов, доля опыта (правило
  штрафа за отставание, а не прогноз), золото и опыт в час числом. Прогноз
  худшего боя рядом с пресетами привала остаётся: это настройка
  собственного правила игрока, а не ворота в контент.
- Боевая сцена — главный элемент экрана и видна ВСЕГДА, в любом разделе.
  Постоянная зона — три блока сверху вниз в одну колонку на любой ширине:
  сцена во всю ширину, ряд иконок действий, строка уровня с полосками.
  Трёх колонок (герой / сцена / умения) больше нет: делить ширину со сценой
  значило показывать бой в трети окна. Статы и лог — в выдвижках «Герой» и
  «Журнал» поверх нижней части экрана. На мобильном вкладки разделов
  прилипают к низу.
- Пропорции сцены держит РАМА (`ui/BattleScene`), а не картинка: 4:3 на
  мобильном, 16:9 от 720px. Содержимое сцены растянуто по раме абсолютно и
  сдвинуть раскладку не может.
- Разделов ЧЕТЫРЕ (`SECTION_IDS` в `stores/ui.ts`): Развитие, Сумка, Мир,
  Настройки. «Персонаж» переехал в выдвижку «Герой» рядом с «Журналом»:
  статы и экипировка нужны поверх боя, а не вместо него. Число закреплено
  тестом `stores/ui.test.ts`. Активный раздел НЕ сохраняется — это «где я
  сейчас», а не настройка.
- Кнопки умений живут в `ActionBar` под сценой, а не в разделе. Там же
  единственный на игру `svelte:window onkeydown`: спрячешь бар во вкладку —
  хоткеи 1/2/3 умрут глобально.
- ТЕКСТОВЫЙ РЕЖИМ — полноценный режим, а не заглушка: в нём на месте сцены
  боевая панель, и игра проходится целиком без картинки. Включается ТОЛЬКО
  настройкой (`'on'`); автоопределения нет и не нужно — двумерной сцене
  нечем не завестись, ей хватает обычных элементов страницы. В текстовом
  режиме сцена РАЗМОНТИРОВАНА, а не спрятана (закреплено `budgets.spec.ts`).
  `?scene=off` сильнее любой настройки.
- Настройки интерфейса (текстовый режим, лимит кадров) лежат в СВОЁМ ключе
  localStorage, а не в сейве: это свойства машины, а не прогресс. Экспорт
  сейва не должен увозить на другой компьютер лимит кадров слабого ноутбука.
- Лимит кадров игровое время НЕ меняет: пропущенный кадр не двигает точку
  отсчёта, накопленное придёт следующим кадром целиком. Закреплено тестом.
- Мобильный: область нажатия не меньше 44px, по горизонтали не вылезает
  ничего ни на одной ширине.

## Боевая сцена (2D)

- Бой рисует ДВУМЕРНАЯ сцена `src/lib/render2d/`: обычные элементы,
  CSS-трансформы и классы состояний. Движка нет: ни three, ни WebGL, ни
  канвы. Сцена заводится везде, где открывается страница, и падать ей нечем —
  поэтому нет ни `reportSceneFailure`, ни автоопределения текстового режима.
  Слои сверху вниз по стеку: фон полосы уровней → спрайт моба → спрайт
  героя → слой эффектов → всплывающие числа. Рама вокруг (`ui/BattleScene`)
  держит пропорции и подпись с именем и здоровьем моба и про рендер не знает.
- ЖЕЛЕЗНОЕ ПРАВИЛО: сцена ТОЛЬКО ЧИТАЕТ игровое состояние и никогда в него
  не пишет. Из `stores/game` ей позволена ровно подписка `gameState`, ни
  одного экшена; всё, что она берёт, собрано одной чистой функцией
  `render2d/model.ts`. Закреплено тестом по исходникам папки. Таймеров
  компонента (`setTimeout`/`setInterval`) в сцене нет — тоже тест.
- ВЕСЬ БЮДЖЕТ ДВИЖЕНИЯ — НА УДАР, НЕ НА ПОКОЙ. Замах виден по отведённой
  руке бьющего, попадание — вспышка на цели, короткий сдвиг и число, крит —
  то же крупнее и цветом предупреждения, умение отличается от автоатаки
  цветом следа и числа, лечение — кольцо у ног героя и зелёное число,
  смерть моба — короткое затухание, привал — своя фаза сцены с подписью,
  а не пустая площадка. Длительности — константы в `data/render.ts`.
- Эффекты — это КЛАССЫ СОСТОЯНИЙ С МЕТКОЙ ВРЕМЕНИ, снимаемые в кадре
  игрового цикла, а не CSS-анимации: под `prefers-reduced-motion` глобальный
  стиль режет длительности до миллисекунды, и ключевой кадр не был бы виден
  вовсе. Сама настройка уважается: тряска и сдвиги под ней обнуляются,
  вспышки и числа остаются.
- Всплывающие числа идут от цели вверх, одновременных не больше
  `FLOATER_LIMIT` (на телефоне `FLOATER_LIMIT_MOBILE`); при переполнении
  отбрасывается новое, а не вытесняется старое. Спрятанная вкладка
  (`document.hidden`) очередь чистит.
- Спрайты и фоны — ДАННЫЕ (`data/sprites.ts`): путь, автор, лицензия,
  «архетип моба → спрайт», «полоса уровней → фон». Сейчас это цветные
  силуэты-заглушки, но реестр настоящий и держится `content:check`: файл
  существует, у каждого архетипа из пулов зон есть спрайт и нет мёртвых
  строк маппинга, полосы фонов идут подряд с первого уровня без дыр и
  нахлёстов. Босс идёт своим силуэтом независимо от архетипа, неизвестный
  архетип — запасным.
- Позы для эталонов: `?debug=1&state=<пресет>&pose=<idle|swing|hit|crit|heal|rest>`
  застывают на пике эффекта и сравниваются с эталоном попиксельно — 2D это
  позволяет. Без пресета `pose` не работает: в живой игре застывшая поза
  была бы ложью о бое.
- Цвета сцены — из `ui/tokens.css` через `var(--…)`, как у любого компонента;
  второго набора цветов у игры нет. Что НЕ из токенов — сами спрайты и фоны:
  это картинки-ассеты, а не величины интерфейса, тот же довод, что и у
  цветов редкостей в `data/rarity.ts`.
- Бюджеты закреплены тестами (`tests/budgets.spec.ts`): за полчаса игрового
  времени узлы DOM не растут больше чем на 5% — для сцены из обычных
  элементов это и есть весь бюджет памяти, спрайты и числа — тоже узлы; при
  `document.hidden` всплывающих чисел не создаётся; тяжёлый раздел не роняет
  кадры против лёгкого.
- ТРЁХМЕРНОГО СЛОЯ В ПРОЕКТЕ НЕТ. Он удалён целиком: `render3d/`, three,
  загрузчик моделей, GLB-ассеты и реестр клипов. С ним ушло около 200 кБ
  сжатого бандла и 8.5 МБ моделей. Библиотеку такого веса обратно не пускает
  CI: джоб `build` держит порог основного куска (900 кБ), и движок его
  пробивает сразу. Возвращать 3D — отдельное решение владельца, не правка.

## Скриншоты и визуальная регрессия

- `?debug=1&state=<пресет>` грузит заранее заданное состояние из
  `game/__fixtures__/presets/` и НЕ запускает игровой цикл: снимок обязан
  быть воспроизводимым до пикселя. Без `?debug=1` параметр не работает,
  неизвестное имя откатывает к обычной игре, а не к пустому экрану.
- Пресет — обычный сейв, поэтому читается той же цепочкой миграций, что и
  сейв игрока. Собираются они настоящими функциями игры (`build.ts`), так что
  застыть в невозможной форме не могут.
- Сид случайности в сейве НЕ хранится, поэтому режим съёмки пришивает свой
  (`SCREENSHOT_SEED`) и заново спавнит моба: иначе каждая загрузка давала бы
  другого противника и другую высоту страницы.
- Поверх пресета прокручивается `SCREENSHOT_TICKS` тиков — иначе лог боя пуст
  и снимок выглядит как сломанная игра. Число входит в определение эталона.
- Анимации выключены глобально под `prefers-reduced-motion` (Playwright
  открывает страницу именно так), живая полоска витрины при этом замирает.
- ДВА РЕЖИМА СЪЁМКИ, и ОБА сравниваются с эталонами попиксельно.
  `?scene=off` убирает боевую сцену и оставляет интерфейс с текстовой
  панелью: снимки разделов от сцены не зависят. Без `scene=off` снимается
  тот же экран с двумерной сценой — она рисуется обычными элементами и
  векторными спрайтами тем же растеризатором, что и остальная страница,
  поэтому воспроизводима до пикселя. Прежний запрет сравнивать сцену
  относился к WebGL и ушёл вместе с ним.
- ПОЗЫ СЦЕНЫ — отдельный комплект эталонов: `?pose=<idle|swing|hit|crit|heal|rest>`
  на пресете `rich` застывает на пике эффекта. Это эталоны на САМИ ЭФФЕКТЫ,
  а не на раскладку: разъехался замах или крит — падает свой снимок с
  понятным именем.
- Эталоны — `tests/screenshots/`: интерфейс — три пресета × три ширины
  (390/768/1280), четыре раздела × две ширины (390/1280), выдвижка «Герой»
  и витрина; сцена — три пресета × две ширины (390/1280; у сцены ровно две
  пропорции, 768 повторил бы 1280) и шесть поз на 1280. Разделы снимаются
  на пресете `rich` — на нём ни один из них не выглядит пустым.
- Требования, которые картинка не проверяет, проверяются измерением: на 320px
  `scrollWidth - clientWidth <= 0` (ничего не вылезает по горизонтали) и
  каждая вкладка раздела не ниже 44px.
- Оба комплекта пишутся в `test-results/current` ДО сравнения и уходят
  артефактом при любом исходе: «посмотреть игру до merge» не должно зависеть
  от того, сошлись эталоны или нет.
- ЧТО ЛОВИТ КАРТИНКА, А ЧТО НЕТ: пиксельное сравнение ловит вёрстку, размеры
  и начертание, но НЕ ловит цвет — цветной текст занимает сотые доли процента
  пикселей страницы, и порога, который поймал бы его и пережил чужое
  сглаживание, не существует. Палитру и шкалы стережёт точный снимок токенов
  `tests/tokens.spec.ts` — он падает от любого изменения значения в
  `tokens.css` и показывает, что именно поменялось.
- Версия `@playwright/test` закреплена ТОЧНО: от неё зависит сборка Chromium,
  а значит и отрисовка. Разъедется версия — эталоны начнут врать. Поэтому же
  в CI берётся браузер из кеша Playwright, а НЕ системный chromium раннера:
  «не качать лишний раз» решается кешем, а не другой сборкой.

## Golden-тест

`src/lib/game/__tests__/golden.test.ts` прогоняет час симуляции с фиксированным сидом
и сравнивает снимки с эталоном `__snapshots__/golden.json`. Он ловит непреднамеренные
изменения игровых чисел: упал golden — рефакторинг изменил поведение, чини код.
Если PR меняет баланс осознанно — удали эталон, прогони тест дважды, закоммить новый
`golden.json` в том же PR и объясни в описании PR, что изменилось и почему.

## Как проверяется работа

У владельца проекта нет локальной среды и нет превью. Игра видна только по адресу
https://Peppapiggreedy.github.io/idle-rpg/ после merge. Поэтому в конце каждого ответа
пиши раздел «Как проверить» — 2–4 конкретных действия на живой странице и что должно
быть видно.
